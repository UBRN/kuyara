# kuyara architecture

## Current workspace

The stack and workspace layout are documented in the [`README.md` Stack section](../README.md#stack).

## Mobile boundaries

The mobile app uses Expo Router and managed Continuous Native Generation, so native projects are generated from Expo configuration rather than stored in the repository. The app config pins iOS 26.0 as the minimum supported version. This is a recorded decision, not a pass-through of Expo SDK 57's own 16.4 floor; see [ADR 0011](adr/0011-minimum-ios-26.md). It introduces no iOS-only shared-code assumption.

As product features are added, mobile code is organized feature-first while preserving presentation, domain/application, and data boundaries. React components render state and emit user intent; use cases coordinate behavior; repositories isolate SQLite and external data. Domain models, local records, and API DTOs remain distinct and use explicit mappers. A feature's repository and provider contracts and their error types live in its domain or application layer and the data layer implements them, so an application module imports its own feature's data only from a provider or loader.

Expo SQLite owns the implemented local profile, its preferences, and profile-owned wardrobe items. Hooks or narrow contexts own transient UI state. SQLite is the device-side working database rather than the product's permanent authority: for a signed-in person Supabase Postgres is authoritative for account-backed data and SQLite keeps its read-and-write-first role. See [Accounts and sync](#accounts-and-sync).

Wardrobe data remains durable local state, but [ADR 0005](adr/0005-catalog-only-recommendation-candidates.md) removes it from recommendation inputs. Recommendations assemble catalog candidates independently from Wardrobe loading or ownership state.

Remote weather request state is a deliberate exception to the project's TanStack Query ownership rule. The weather application controller owns per-location coalescing, last-valid snapshot preservation and the 30-minute freshness boundary. The place search controller (`apps/mobile/src/features/weather/application/place-search-controller.ts`) owns place search request state, and the AI probe hook (`apps/mobile/src/features/recommendation/application/use-ai-probe.ts`) owns its probe request state. Each has one owner. TanStack Query remains the intended owner for future remote state these controllers do not cover.

`components/ui` is the leaf primitive layer: its production files import no `features/*` module, so a control that needs a feature's value takes it as a prop or a child (the colour well draws whatever face its caller hands it, and the condition symbol's hook takes a motion that the weather domain's `conditionSymbolMotion` chooses). The garment art, which draws feature vocabulary, lives in `src/garment-art/` beside `features/`: the silhouettes, the board renderers, the tiles and the Closet palette's swatches. Features import it through its `index.ts`, and it names another feature only through that feature's domain layer. Both rules are held by `architecture-invariants.test.mjs`.

The local-profile vertical slice follows this concrete dependency flow:

```text
Expo SQLite database open + ordered migrations
        ↓
project-owned SQLite executor boundary
        ↓
SQLite profile local data source and persistence record
        ↓
local profile repository and domain profile
        ↓
profile application controller/provider
        ↓
onboarding gate, Settings, localization/theme preferences, Today navigation
```

Only the infrastructure adapter imports `expo-sqlite`. The data source owns SQL and row mapping; the repository validates and maps persistence records into domain values; the application controller owns loading, failure, saving, and refreshed profile state. Routes and presentation components depend on that application contract and do not know table names, columns, or SQL.

### Database migrations

`PRAGMA user_version` records the schema version. The database is opened and migrated once per process: the open promise and the migration run are memoized inside the SQLite boundary, so the six composition roots share one connection and one migration run. Bootstrap enables foreign keys and WAL on that shared connection and sets a five-second busy timeout, reads the current version, and applies each pending migration in ascending order through a transaction the boundary owns: it opens its own connection, sets the same busy timeout and `foreign_keys` on, and takes the write lock up front with `BEGIN IMMEDIATE` so a contending writer waits instead of failing. A migration updates `user_version` inside the same transaction and only after its schema work succeeds. Completed migrations are safe to call again; a newer unsupported version or failed migration surfaces a bootstrap error without deleting or recreating the database.

Version 1 creates only `local_profiles`. `singleton_key` is constrained to the sole value `1` and is the primary key, while `id` is a unique generated UUID. Stable, locale-independent checks constrain clothing (`womens`, `mens`, or null before onboarding), language (`system`, `tr`, `en`), theme (`system`, `light`, `dark`), and the integer onboarding flag. Lifecycle timestamps use UTC ISO-8601 text. `deleted_at` is nullable to preserve the settled local-data record shape, but profile deletion and soft-delete workflows are intentionally not implemented.

Version 2 leaves version 1 unchanged and adds `wardrobe_items`. Its UUID primary key is associated with `local_profiles.id` through a restrictive foreign key. Nullable `name`, `color`, `photo_relative_path`, and `deleted_at` columns are distinct from the required stable category and UTC ISO-8601 lifecycle timestamps. A database check restricts category storage to `top`, `bottom`, `one_piece`, `outerwear`, `footwear`, or `accessory`.

One composite index over `(local_profile_id, deleted_at, updated_at DESC)` supports the profile-scoped active and explicitly deleted access patterns without speculative indexes. The table and index use idempotent creation inside the migration transaction. Version 2 advances `user_version` only after both succeed; failure rolls back the new schema while preserving version 1 profile data and its schema version.

Version 3 leaves versions 1 and 2 unchanged and adds nine nullable columns to `wardrobe_items`: `garment_type_id`, `color_family`, and explicit thermal, water, wind, breathability, arm-coverage, leg-coverage, and traction overrides. SQL checks constrain each non-null enum value, while `garment_type_id` intentionally has no SQL list or foreign key because the canonical catalog is bundled TypeScript data. Existing rows retain their identity, owner, category, display values, photo path, lifecycle timestamps, and deletion state with every new column null; no type or property is inferred during migration.

Version 4 leaves the earlier schema unchanged and adds one profile-owned active location, location-bound weather snapshots, and their hourly entries. Coordinates are rounded to the nearest `0.01°` and represented as integer hundredths before they cross the location adapter. That is roughly 1.1 km north-to-south and less east-to-west at kuyara's sample latitudes: useful for local weather while avoiding unnecessary device precision. The normalized pair also forms device-location cache identity and can be converted back to decimal degrees by a future Worker request mapper. Manual selections store a stable catalog ID; device selections store normalized coordinates, time zone, approximate/full accuracy, and the locality name their reverse geocode resolved, if any. Raw coordinates, permission diagnostics, and provider payloads are not persisted or logged. Snapshot replacement and hourly replacement are atomic, and retention is bounded to the active location plus the newest previous location.

Version 5 leaves the earlier schema unchanged and adds `recommendation_snapshots`, with one row per `local_profile_id`. Each row stores a UUID `id`, the owning profile, `weather_snapshot_id`, `location_key`, an `ai-assisted` or `deterministic-fallback` generation mode, validated context and outfit JSON, and UTC ISO-8601 creation and update timestamps. A restrictive foreign key associates the unique `local_profile_id` with `local_profiles.id`.

Version 6 adds the required `notifications_opt_in` integer preference to `local_profiles`, defaulting to `0` and constrained to `0 | 1`.

Version 7 adds an `owned | wanted` `entry_state` to `wardrobe_items`, preserves every existing row, and defaults existing entries to `owned`. New entries require a catalog garment type; existing null `garment_type_id` rows remain readable, editable, and deletable as legacy records.

Version 8 rebuilds `local_profiles` to convert the clothing preference into `gender` (`womens` to `woman`, `mens` to `man`) and adds a nullable ISO calendar-date `birth_date`, preserving every other column, dependent row and the onboarding flag; the rebuild runs a `foreign_key_check` on the transaction connection before commit, and a failed rebuild rolls back. Foreign keys are enforced on every connection, the shared one and each transaction connection alike, so `ON DELETE RESTRICT` and the one `ON DELETE CASCADE` on hourly entries are runtime guarantees; the weather data source still deletes hourly entries explicitly so that behaviour does not depend on connection setup. Two red lines follow from enforcement: a migration that rebuilds a parent table must copy the version 8 and 13 recipe (`PRAGMA defer_foreign_keys` and its reset), because dropping a parent bumps the deferred violation counter, and no code adds `INSERT OR REPLACE`, a delete on `local_profiles`, or a new delete on `weather_snapshots` without re-reading the foreign-key graph (the weather data source's existing snapshot deletes remove the hourly rows first). Orphaned rows that older builds left behind stay in place; foreign keys check the row being written, never pre-existing children. Version 9 adds the active location's `display_name` and backfills the sample cities. Version 10 adds the nullable checked `dress_style` and resets onboarding once so existing installs answer it. Version 11 adds the `weather_alert_deliveries` ledger for local weather alerts. Version 12 adds the profile-owned `analytics_consent` state, defaulting existing rows to `undecided` and constraining it to `undecided | granted | withdrawn`. Version 13 rebuilds `recommendation_snapshots` to widen the generation-mode check to `on-device-ai | ai-assisted | deterministic-fallback`, copying every existing row verbatim with foreign keys deferred for the copy so that an orphan already on the device cannot block bootstrap; see [ADR 0034](adr/0034-on-device-ai-selection-through-apple-foundation-models.md). Version 14 adds the profile's one-time weather-alert offer flag and version 15 the morning briefing's own opt-in, both additive and both starting off. Version 16 adds the nullable `weather_snapshots.daily_json` column that holds the daily outlook; every existing row keeps its weather and carries no outlook until the next refresh writes one. Migration 17 (display name and prompt gate) additively adds `local_profiles.display_name TEXT NULL` and `local_profiles.name_prompt_version INTEGER NOT NULL DEFAULT 0`, preserving existing profile rows. Migration 18 (daily styles and day choices) adds `style_aesthetics`, `morning_sheet_enabled`, and `dressing_day_choices`, preserving existing profile rows. Migration 19 (outfit history and departures) adds the nullable daily style override, outfit history, and dressing-day departures. Migration 20 adds nullable `wardrobe_items.color_option_id` and checked uppercase `color_custom_hex` columns without rewriting existing rows; the domain allows at most one choice and derives `color_family` from it. Migration 21 adds the checked `local_profiles.easier_to_see INTEGER NOT NULL DEFAULT 0` switch, preserving existing profile rows. Migration 22 adds the coach-mark tour's gate `local_profiles.walkthrough_version INTEGER NOT NULL DEFAULT 0`, preserving existing profile rows; it is tested from the build 15 schema (version 19) and from a version 21 fixture. Migration 23 adds the outfit detail's one-time swipe hint flag `local_profiles.swap_hint_shown INTEGER NOT NULL DEFAULT 0 CHECK (swap_hint_shown IN (0, 1))`, preserving existing profile rows; it is tested from the build 15 schema (version 19) and from the build 16 schema (version 22).

Schema changes for the approved phases are additive. Phase 3 adds profile `display_name TEXT NULL` (2 to 30 characters in the domain) and `name_prompt_version INTEGER NOT NULL DEFAULT 0`. Phase 4 adds `style_aesthetics TEXT NOT NULL DEFAULT '[]'`, a validated sorted JSON array of at most three closed ids, and `morning_sheet_enabled INTEGER NOT NULL DEFAULT 1`. Phase 8's migration 22 adds `walkthrough_version INTEGER NOT NULL DEFAULT 0`. Migration 30 adds the App Store rating request's gate `review_request_version INTEGER NOT NULL DEFAULT 0`. Each versioned prompt gate (`name_prompt_version`, `walkthrough_version`, `review_request_version`) compares the stored integer with its code version and stores that version on completion or dismissal; the rating request stores it when the request is made. Migration 23's `swap_hint_shown` is a boolean flag rather than a versioned gate: 0 until the outfit detail's swipe hint starts to move, then 1. See [ADR 0036](adr/0036-display-name-and-one-time-prompt-gate.md).

### Wardrobe application and persistence boundary

The wardrobe slice follows the established executor boundary and adds a narrow feature-local application controller for its list and forms:

```text
Wardrobe routes and localized presentation
        ↓
feature-local controller/provider and explicit form mapper
        ↓
wardrobe domain model and input invariants
        ↓
local wardrobe repository and sanitized error model
        ↓
explicit domain/category ↔ persistence record mapper
        ↓
SQLite wardrobe local data source with profile-scoped bound SQL
        ↓
project-owned SQLite executor
```

The domain item and SQLite record are separate types. The mapper explicitly converts the stable category representation and rejects invalid stored enums, timestamps, nullable values, or non-canonical photo paths. The repository owns client UUID and clock dependencies, input normalization, profile isolation checks, patch-style domain updates, and stable `invalid-input | invalid-data | not-found | unavailable` errors. SQLite and its raw errors do not cross this boundary.

The local data source owns fixed-column parameterized create and update statements. Updates preserve the UUID, `local_profile_id`, and `created_at`; successful writes refresh `updated_at`. Soft delete atomically sets `deleted_at` and `updated_at`, after which normal get/list/update operations ignore the row. A separate explicit read can include deleted items for tests or a future recovery workflow.

The controller owns initial loading, stable active-list refresh, retry state, and one in-flight mutation. It injects the ready local profile ID into repository calls, refreshes the list after successful writes, rejects a second save while one is in flight (it does not coalesce them), and rejects malformed route UUIDs before repository access. Presentation never receives SQLite records or SQL.

The form model contains only the editable optional name, required catalog type, color family, and seven nullable overrides. Its pure mapper derives applicable overrides from non-null catalog defaults, clears unsupported values, and deliberately omits UUID, owner, lifecycle, deletion, legacy `color`, and photo fields. Patch-style updates therefore preserve hidden fields. A confirmed type change resets explicit overrides and leaves no override, so the catalog defaults apply.

Photo persistence is deliberately path-only. The domain and record store a normalized forward-slash relative path into app-private document storage, never a blob, base64 value, absolute path, or `file://` URI. A feature-local photo manager coordinates three injected adapters: the system picker, the contextual image processor, and private storage. The picker has two sources, the photo library and the system camera, and both return the same picked shape, so a captured photo runs the same processing and staging as a chosen one. Selection and capture request one image without base64 or EXIF; processing preserves aspect ratio, limits the long edge to 1600 pixels without upscaling, and writes JPEG at 0.8 quality, then deletes the picker's original when it sits in the app's private cache, whether processing succeeded or failed; an original outside the cache is never touched, and a missing or undeletable one does not fail the photo. The library picker needs no permission. Camera access is requested only when the user taps Take photo: access that is off (iOS reports a restricted camera as denied) rejects with the closed reason `denied`, and an iOS device without a camera, the Simulator, rejects with `unavailable` after the permission answer and before the camera is launched, because UIKit raises an uncatchable exception for a missing camera source and expo-image-picker does not check; on Android, expo-image-picker's rejection for a missing camera app (`ERR_MISSING_ACTIVITY_TO_HANDLE_INTENT`) maps to `unavailable`. The form shows a localized note for either reason, with the platform's settings link for `denied`, and the library keeps working; a cancelled capture is no change. Managed staging files live in private cache storage and UUID-named canonical files live below `kuyara/wardrobe/photos` in the private document root.

Create and replace operations copy a staged photo to a new canonical path before the SQLite write. A failed write removes the new canonical file while retaining staging for retry; a successful write clears staging and only then cleans up the prior managed file. Removing a photo follows the same database-first rule. Cleanup failure never reverses a confirmed database write, unmanaged paths are never deleted, and soft deletion confirms the database write first, then removes the managed private file, and only then clears the stored path, so the tombstone row keeps naming a file that could not be removed and the next launch retries it; the row itself stays for future cross-device deletion. A launch sweep removes what those paths still leave behind (a failed removal after a save, a copy the app was killed after, a partial copy that could not be deleted). Once per launch, after the pending removals are retried and while no save is in progress, the controller lists the managed photo directory, then reads every path any row names (deleted rows, other profiles' rows and rows the mapper rejects included, compared in lower case), and deletes only the files that nothing names, that are older than 24 hours and whose modification time is known, through the same guarded delete. A save started during the sweep waits for it, and a file a save is about to name is never swept because the sweep never runs beside a save. It deletes only canonical `<uuid v4>.jpg` files directly in `kuyara/wardrobe/photos`, never a subdirectory or another feature's directory, and it also removes staged files in the private cache older than one hour. A failing list, read or delete leaves the Closet ready and is reported once through the existing cleanup warning; the next launch tries again. Presentation receives only renderable URIs through the application boundary; it does not import picker, image-manipulation, or file-system APIs. Photos remain local and are never sent to the Worker, AI providers, analytics, or another network service. Photo URI resolution treats missing or corrupt private files as no photo and keeps the Closet usable.

The six categories continue to express only structural outfit roles. A versioned, immutable mobile catalog supplies canonical garment types and validated coarse defaults without copying those definitions into SQLite. Wardrobe rows store the selected type reference, an optional canonical color family, and only explicit user overrides. Weather, fabric, formality, selected runtime layer role, brand, purchase, AI, and provider metadata remain outside the item schema. A future remote sync adapter will map separate remote records and complement rather than replace SQLite.

The research-backed taxonomy and version 3 contract are specified in [`clothing-taxonomy.md`](clothing-taxonomy.md). Mobile-only values and Zod schemas live in the catalog domain because no Worker API contract uses them yet. The catalog validator enforces ID, category, coverage, localization, applicability, and deprecation invariants before exporting deeply frozen definitions.

An owned item's effective value is its stored override over the current catalog default. No runtime resolver exists: the Closet shows the type and colour, and recommendations never read the Wardrobe. Catalog applicability filters catalog suggestions only and is never consulted when reading an owned item.

ADR 0005 governs recommendation assembly: neither resolved owned items nor wanted items become candidates.

### Foreground location and local weather boundary

The Weather tab follows a feature-local dependency flow:

```text
localized Weather presentation
        ↓
weather application controller/provider
        ↓
weather repository and validated domain snapshots
        ↓                         ↓
SQLite weather data source        provider interface
                                  ↓
                         Worker HTTP provider adapter
                                  ↓
                    shared weather v2 Zod contracts
                                  ↓
                    Worker provider chain
             WeatherKit → Open-Meteo → OpenWeather
```

The controller owns bootstrap, location-selection intent, the permission request, foreground-only device lookup, fresh/stale evaluation, refresh coalescing, location-switch races, and foreground revalidation. Foreground revalidation re-acquires the device location once per event while it is the active one and permission is granted, and replaces the active location when its normalized key or time zone has moved, or when the lookup resolved a locality name the stored location does not carry, which is how a location stored before names existed acquires one. A changed approximate/full accuracy also replaces it, keeping the stored name when the lookup resolved none. A failed lookup is silent and leaves the cached snapshot rendered. The stale snapshot's refresh starts at once, in parallel with that lookup, so it never waits for the location fix; a place the lookup then replaces gets its own refresh from the selection, the old place's late result is not published, and a selection whose cache read a refresh of the same place overtook keeps the newer snapshot. Because freshness ages with the clock rather than with a state change, Today and Weather re-run the same revalidation when they regain focus, which starts the identical coalesced background refresh. It reads permission state during bootstrap without prompting. The native foreground permission request occurs only when the user selects device location, and that tap requests it directly whenever the platform still allows asking; permanently denied access offers the platform Settings action. Opening Settings from that card sets a one-shot intent held in memory only: the next return from the background ends it, and when access was granted there it acquires the device location as the tap would have. A manual pick, dismissing the card or a new tap clears it first, and a cold launch never carries it. Manual selection remains available without permission.

The `expo-location` adapter is the only feature code that imports the native location module. Raw platform positions stay inside that adapter and are reduced to normalized coordinates plus approximate/full accuracy before returning. The single reverse geocode that resolves the time zone also yields the locality name the location carries: the address's city, or its subregion when the city is unknown, trimmed and length-checked by the shared display-name schema. The rest of the address, the street above all, never leaves the adapter, and a geocode that times out or resolves nothing returns a location without a name rather than no location. Shared domain, repository, controller, and presentation code remains platform-neutral. iOS requests only When In Use authorization and defaults to reduced accuracy. Android declares coarse location while explicitly excluding fine, background, activity, and location foreground-service permissions for this scope.

SQLite is the durable source of truth for the active selection and the last valid snapshots. A cache is fresh through exactly 30 minutes, stale after that boundary, and still rendered while a background or manual refresh runs. A `fetchedAt` in the device's own future is tolerated up to five minutes and treated as fresh, because the Worker stamps it from Cloudflare's clock and an ordinary device clock runs seconds behind; beyond that tolerance the snapshot is rejected as invalid. Without the tolerance a device a few milliseconds slow rejects every live refresh from the deployed Worker. Failed refreshes never erase the prior valid snapshot, the daily outlook included. A place is its location key together with its time zone: a move to another zone under the same key is a new place, so a snapshot stored for the old zone is neither shown nor treated as fresh for it, and its refreshes do not coalesce with the old zone's. A refresh request that joins one already running keeps the refreshing state on, and a cache read that fails while a place is being selected counts as no cache, so the new place is still fetched. A refresh result is published only if it still belongs to the selected location; the repository validates time zone, source/location identity, measurements, and the shared ordered 36-hour window rule before persistence. Reads retain compatibility with already-persisted ordered same-local-day snapshots from the earlier contract.

The daily outlook is persisted as one JSON document in the schema version 16 `weather_snapshots.daily_json` column, the way a recommendation carries its context and outfits, because it is read whole, never queried by field and replaced entirely on every refresh; a child table would have bought a second cascade and a second line in the prune for nothing. The column is nullable, and null is the only way a snapshot says it carries no outlook: a row written by an earlier build, or a source that served none. The repository owns both the parse and the validation, and an unreadable or partly invalid document costs the outlook alone, never the snapshot the screen needs to render, which is why a week missing one day is dropped whole rather than drawn short. A domain snapshot therefore carries `daily` as an optional array, absent rather than empty when there is nothing to show.

The Weather screen draws the first five of the contract's seven days in its own card below the hourly one, in the ADR 0028 row anatomy: the day's condition glyph in the P1 resolver's day ink, the weekday from the `dateKey` read as a calendar date in UTC, the precipitation cell (the measured amount beside its chance, the chance alone when the provider reported no amount, and nothing at all when the day carries neither), the low and the high through the single temperature formatter, and a 6 point rail (8 with Easier to see) whose capsule spans that day's range inside the week's own minimum and maximum, coloured on the fixed temperature scale the hourly line shares, with a 10 point dot (12 with Easier to see) for the current temperature on today's row. Every row is one accessible element whose label names the weekday, the localized condition, the range and the chance, so the empty cell and the colour are never the only signals; above `fontScale` 1.5 the range stacks under the day.

The application composition uses the network-backed Worker provider adapter. It sends only normalized coordinates and the selected IANA time zone to `POST /v2/weather`, validates success and stable error bodies with the shared Zod contracts, then maps valid data into the existing provider snapshot. The request and the error body are still v1's; only the success schema is v2's, so a response that adds a key this binary does not know is still stripped and accepted, and a response with no `daily` array is an `invalid-response` rather than a snapshot missing its outlook. The mapper restores the device-local location key from the request context; profile identity, catalog identity, permission state, and accuracy remain outside the API. The deterministic in-process provider is available to focused tests only and is never the application composition.

Snapshots and weather rules keep Celsius values. Presentation shows the unit the profile's device-only `temperature_unit` choice names; under `system` it follows the device's Temperature setting, using the device locale when no explicit unit is set. `domain/temperature-unit.ts` and `domain/wind-speed.ts` each resolve a stored choice against the device in one place; the localization provider hands the result to every screen, and the background alert task resolves the stored choice itself.

Place search uses `POST /v1/places/search` through `WorkerPlaceSearchDataSource`, with shared request/result/error Zod schemas (strict request, tolerant result and error, as above). The Worker alone calls the assumed Open-Meteo Geocoding provider, validating raw fields and mapping at most five places to stable `place.<positive decimal id>` ids, display names, region/country lines, hundredth-degree coordinates and a nullable IANA time zone. Each search makes one upstream call with a four-second timeout; when the typed query answers fewer than the requested places and contains a lowercase i, the same deadline covers at most three further calls with dotless-ı spellings (each single position, then every position), because Open-Meteo folds every other Turkish letter but not ı, and their unseen ids are appended after the unchanged typed answer, with a failed retry returning what the typed query gave. It has its own per-IP limiter budget, so a burst of typed searches cannot exhaust the weather refresh budget or the reverse, and it fails closed if that limiter is unavailable. A successful, complete place search result is kept for 24 hours in the Workers Cache API under a synthetic key built from the query, limit and language (never the caller), read after the limiter so a cache hit spends the caller's budget like a miss, and an error, a rate-limited answer or an answer whose spelling top-up failed is never cached. Query text stays in the POST body and is not logged; responses carry controlled `open-meteo` and `geonames` attribution identifiers for the picker. Manual ids accept validated `sample.<slug>` or `place.<positive decimal id>` shapes. SQLite v9 adds the active location's display name and backfills the three sample cities. The picker screen is the `/weather/location` route, which renders `LocationSelectionControls`: it shows that display name, renders the attribution as the result section's footer, and its `PlaceSearchController` drops a result without a time zone before a manual selection reaches the weather repository.

The Worker origin resolves from `EXPO_PUBLIC_KUYARA_WORKER_BASE_URL` when set. Development otherwise defaults to `http://127.0.0.1:8788` for the iOS Simulator, or `http://10.0.2.2:8788` for the Android emulator; physical devices need an explicit reachable LAN origin ([Development build on the physical iPhone](testing.md#development-build-on-the-physical-iphone)). The production EAS profile sets the deployed HTTPS origin. This configuration changes only the remote provider boundary: SQLite remains the source of truth, and exact 30-minute freshness, cache-first rendering, request deduplication, manual refresh, last-known-good preservation, and failure presentation remain owned by the existing controller and repository.

The mobile provider boundary classifies failures without depending on the Worker adapter: transport rejection is `network`, a validated non-success response is `service`, and malformed success or error data is `invalid-response`. The application maps only `network` to an offline outcome; every other provider or persistence failure becomes unavailable. A cached snapshot and its active location remain visible for either outcome, and only a successfully validated and persisted retry clears the failure. Local repository failures during bootstrap still use the existing screen-level load error rather than appearing as network failures.

### Local profile lifecycle

The data source performs get-or-create in an exclusive transaction. It reads the singleton first, then uses `INSERT OR IGNORE` with a newly generated Expo Crypto UUID v4 and reads the winning row. Concurrent calls (repeated React/Strict Mode calls) share one in-flight read and create, and a call after it settles reads the stored row again, so a write made outside the data source, such as a sync pull, shows on the next read; the schema constraint protects across data-source instances. The UUID is never regenerated once a row exists and is never shown or logged.

`local_profiles.singleton_key` is the primary key under `CHECK (singleton_key = 1)`, so a second local profile on one device is impossible. [ADR 0041](adr/0041-optional-accounts.md) keeps that rule: an account links to the one device profile through a separate device table rather than through additional profiles (see [Accounts and sync](#accounts-and-sync)).

A new profile has null gender, dress style, and birth date, system language, system appearance, and `onboarding_completed = 0`. Onboarding completion updates gender, dress style, birth date, completion state, and `updated_at` in one transaction. Settings uses one explicit transactional update per selected preference. Application state changes only after SQLite succeeds; failures restore the previous domain profile and presentation shows localized, non-technical feedback.

The static year range is 1900 to 2100; the domain validates real calendar dates and rejects future dates against the local calendar. The profile owns gender, persistent dress style, birth date, and the approved optional display name, closed style aesthetics, name and walkthrough prompt gates and morning-sheet preference. Daily answers live in `dressing_day_choices`, not a profile JSON field. `ProfileApplicationController` projects `LocalProfile.clothingPreference` through one gender-to-catalog mapping. Birth date drives no product logic. The AI request builder, analytics boundary and telemetry boundary each have a test proving that `displayName` and other free-text profile fields cannot appear in output. See [ADR 0031](adr/0031-dress-style-is-the-formality-signal.md) and [ADR 0036](adr/0036-display-name-and-one-time-prompt-gate.md).

The persisted record, domain profile, and UI state are deliberately distinct. The record retains integer booleans, storage column values, and `deleted_at`; the domain exposes strict preference unions, a boolean completion value, and no deletion field; presentation receives only the controller’s domain state and actions.

Today lives under `apps/mobile/src/features/today/`.         ↓

The composer's public entry is `features/recommendation/domain/outfit-composition.ts`, and callers import from it. `recommendOutfits` is a pure function: it reads no clock, performs no I/O, and returns the same result for the same input regardless of candidate order. Recommendation cache identity is weather snapshot identity, derived clothing preference, the dressing day's resolved formality, sorted closed style aesthetics, catalog version and day variant. Generation occurs after an active-location, derived clothing-preference or dress-style change, a bundled catalog-version change, a style-aesthetics or keyed daily-formality change, the start of a new dressing day, an expired coverage window on foreground open, or an explicit user request. The existing `localDayKey` from the recommendation controller, derived through the weather domain's `wardrobeDayKey`, is the only dressing-day clock: bare local date from 04:00 to 18:00 and that date plus `:evening` through 04:00 the next morning. Morning sheet eligibility, daily formality, outfit history and History's Sunday-evening week summary all use that key; history stores its bare-date portion, so only "Wore this today" can replace a morning record with an evening look. The AI regeneration budget uses the calendar date of that key, sharing five attempts between day and evening. `wardrobeDayWindow` remains the dressing-day and weather-alert horizon. A saved departure, and the formality chosen with it, are keyed by the device clock's dressing day of the departure instant; the departure's `time_zone` bounds only its coverage window, so a place in another zone never files it under a day Today does not read. Clothing requirements use a separate coverage window that begins now or at a saved departure and ends by the departure hour in the snapshot time zone. The first four hours drive the main outfit; a short later cool spell is optional, while sustained or severe cold remains mandatory. Coverage start and end are optional persisted context fields, excluded from the coalescing identity. An unanswered evening key has its own pending state; Today opens its sheet empty. A confirmed re-ask writes its answers and starts one reserved `regenerate` refresh, and approved-trigger evaluation waits for it so its own new day type never starts a second generation. A birth date or display-name change triggers nothing. In an evening dressing day, after a foreground open of Today and once the evening's outfit is settled, `TomorrowPreviewController` selects the next dressing day's outfit for a departure at 08:00 on the place's clock on the following date (`previewDepartureAt`, in the snapshot time zone like the coverage window it opens), with the profile dress style and the Settings styles, the evening outfit's three options excluded, and only when the hourly forecast covers that whole coverage window. It claims the day once in `tomorrow-preview.json`, an app-private file beside the re-ask counter, so a restart or a failed selection never selects again that evening; the record is validated by `LocalRecommendationRepository` over that file exactly as over SQLite. It shares the routed AI client and the deterministic fallback but not the controller's state, phase, analytics or telemetry. When the morning's approved generation reaches the AI chain (any trigger but `regenerate`), the controller first asks `reusablePreviewRecommendation` whether the stored preview answers the same question: same dressing day, place, clothing preference, resolved formality, sorted styles, catalog version, day variant and requirement set, a stylist-selected mode, and every pick among the options now offered. If so it saves that selection under the morning's own weather snapshot and context; otherwise it asks as before. Today reads the persisted recommendation snapshot through `RecommendationApplicationProvider`; the result is tagged `on-device-ai` when the on-device tier answers, `ai-assisted` when the Worker AI call succeeds, and `deterministic-fallback` otherwise. No repository, provider DTO, runtime schema, persistence layer, network client, or global state container is introduced by Today itself; it consumes application providers mounted at the root.

Structured insight rules live in `features/weather/domain` and are exported through that feature's domain boundary for recommendation to read. Results are kinds and numeric parameters, never text; Today maps each kind to a whole-sentence localization key. The first-generation runway is derived presentation state: the controller sets `showFirstGenerationOverlay` only when a recommendation for the current dressing day is absent and a generation is in flight, and hands the runway no outfit while it waits. ## Worker and contract boundaries

The [Apple Developer Program](product-decisions.md#apple-developer-program) membership is active. The checked-in composition serves real weather through WeatherKit, then Open-Meteo, then the configured OpenWeather fallback; the deterministic sample provider is test-only and is never a production fallback.

The Worker is the server-side boundary for weather and AI provider calls, credential protection, validation, and operational limits. Its mobile API includes weather, AI recommendation, and active-probe routes plus non-AI liveness and configuration-only AI readiness. `POST /v1/weather` and `POST /v2/weather` accept only normalized integer hundredth-degree coordinates and an IANA time zone; neither accepts a profile ID, location key, permission state, accuracy label, or raw native location payload.

| Route | Purpose |
| --- | --- |
| `POST /v1/places/search` | Place search |
| `POST /v1/feedback` | Optional user-submitted feedback, unavailable until its D1 binding is configured |
| `POST /v1/weather`, `POST /v2/weather` | Frozen v1 weather and daily-outlook v2 through one provider chain |
| `POST /v1/ai/recommend`, `POST /v2/ai/recommend` | Frozen v1 selection and the v2 aesthetics/insight contract through one handler |
| `POST /v1/ai/probe`, `POST /v2/ai/probe` | Bounded active AI probe: v1 for installed binaries that read a closed provider list, v2 for the chain's first provider |
| `GET /v1/health`, `GET /v1/ai/ready` | Provider-free liveness and AI configuration readiness |

Every route that reads a JSON body stops reading once the body passes the route's byte limit and answers its existing `invalid_request`, so an oversized body is never buffered whole: 256 bytes for weather, 1,024 for place search and 65,536 for AI recommend, each at least 1.5 times the largest compact request a client sends after parsing it with the strict contract, and 4,096 for feedback and account deletion.

The feedback route is separate from shipped response shapes. Its strict request contains only a random submission UUID (one per form submission, reused when the person retries the same text, never a device or user identifier), message text (at most 1,000 characters), app version in the store format `0.MINOR.YYYYMMDD`, platform and locale; a retry with a known submission UUID stores nothing and still answers success. Its response schemas follow the other routes: unknown keys are stripped and a new error code reads as `unknown`. The Worker caps the JSON body at 4,096 bytes, applies a dedicated per-IP rate limit of 3 requests per minute, and stores only those fields plus the creation time in D1, with the submission UUID as the row ID. It never stores the IP or logs the message. Without both the D1 and limiter bindings it returns a stable unavailable error. The mobile Settings form and row remain behind a disabled flag while the database, disclosure and Worker deployment are pending.

`packages/contracts` owns the Zod request, success, and stable error schemas plus their inferred TypeScript types. Request schemas are strict and the Worker owns them; success and error schemas strip unknown keys, so a published Worker may add a response field and installed binaries built from commit f0ab923 or later accept it, while a new enum member is additive only where a named unknown branch exists: binaries built from 221cd2a or later read a new `origin.sourceId` or a new weather, place-search, feedback or account error code as `unknown`, the AI error schema is deliberately a closed enum so a new AI error code breaks every installed binary and ships only on a new route, a new condition code or place-search attribution id breaks every installed binary, and while build 8 or 9 is installed every added member is still a breaking change because those binaries read each enum strictly. No provider joins the weather chain before every supported binary carries its attribution key. Binaries built before f0ab923 (build 8 and build 9, both released) carry `.strict()` response schemas that reject any unknown response key at any level, so while one of them is installed every `/v1` response shape is frozen at every level, a changed shape ships on a new route while the old route keeps its exact shape, and adding a field becomes safe only once a binary built from f0ab923 or later is the oldest installed version. The request-side `office_ready` compatibility gate likewise keeps smart outfits ineligible when `dayKind` is absent, and that legacy branch may be removed only when the Release State in `docs/current-status.md` shows that every installed binary sends `dayKind`. The success contract uses the same settled weather condition vocabulary and validates timestamps, measurement ranges, minimum/current/maximum relationships, and one to 38 strictly ordered hourly entries whose timestamps fall from one hour before through 36 hours after `current.observedAt`. Its provenance is `sample | live`. Raw provider payloads, credentials, and internal error detail must never cross it. The one controlled addition is `origin.sourceId` (`sample | weatherkit | open-meteo | openweather`), a non-secret attribution identifier the mobile app maps to localized attribution text; see [Weather provider chain](#weather-provider-chain) below.

The two weather routes are one handler, one strict request schema, one rate-limit key and one provider chain; they differ only in the response schema the snapshot is mapped through, so /v2 can never spend quota /v1 does not. `POST /v2/weather` carries the whole v1 payload plus a `daily` array of one to seven ordered entries, each with the local `dateKey`, a condition code from the same closed eleven, that day's low and high, the precipitation chance and a nullable `precipitationMillimetres` the Worker never invents; its first entry is the observation's local day and repeats the snapshot's own low and high. The origin, attribution and error shapes are v1's, and `/v1/weather` keeps its exact body because the v1 schema has no `daily` key and strips it. A binary reads the daily block only if it was built against `weather-v2.ts`; the deployed Worker therefore has to serve /v2 before such a binary is built.

The Worker route validates the request before invoking an injected provider. The provider returns a provider-neutral internal snapshot, and an explicit mapper validates and converts that model into the shared success DTO. Provider failures and invalid provider values become the same minimal `weather_unavailable` response; invalid requests, unknown routes, wrong methods, and unexpected failures have their own stable codes without localized messages, provider details, stacks, or configuration data.

The checked-in production composition is the real chain described below; the deterministic local mock with its injected clock and explicit `sample` provenance is now a test double only. The route sets `Cache-Control: no-store`, does not log coordinates or request bodies, and is rate limited (see below). Worker observability is enabled, so Cloudflare retains invocation metadata for deployed requests. The Worker's own log statements are structured events with closed names and reason codes, among them provider attempt outcomes (a provider or model identifier, the attempt position and a reason) in `ai-handler.ts`, `probe-handler.ts` and `weather-provider-chain.ts`, shared-cache rejections in `ai-cache.ts`, rate limits and limiter failures in `json-request.ts`, and the daily counters, member allowances and account deletion stages; none prints a request body, so coordinates stay in the unlogged request body. Every real adapter, including WeatherKit, implements the same provider interface and keeps signing, credentials, and raw provider data entirely inside the Worker.

## Approved target composition

The approved [weather provider strategy](product-decisions.md#approved-weather-provider-strategy) and [AI recommendation strategy](product-decisions.md#approved-ai-recommendation-strategy), including their rationale, are canonical in `product-decisions.md`. This section records only where those boundaries and fallbacks live and how they connect.

### Weather provider chain

Design, the pricing basis, and full rationale are canonical in [ADR 0002](adr/0002-real-weather-provider-chain.md) and [ADR 0014](adr/0014-weatherkit-at-the-head-of-the-provider-chain.md); this section records only where the chain lives and how it connects. The chain lives entirely inside the Worker. Mobile keeps depending on the existing provider-neutral contract and gains no provider knowledge.

```text
Worker weather route
        ↓
ordered provider chain: WeatherKit primary → Open-Meteo fallback → OpenWeather fallback
        ↓                              ↓                              ↓
   per-provider adapter          per-provider adapter          per-provider adapter
   raw-response validation, unit and condition mapping,
   timeout, provider-specific error classification
        ↓
existing provider-neutral internal snapshot
        ↓
existing explicit API mapper and shared success DTO
```

WeatherKit sits at the head of this chain as the primary provider and serves live production traffic; OpenWeather is the tail fallback, behind its provider-side cap and Worker credential. The mobile weather domain, its repository, the exact 30-minute freshness boundary, and last-known-good behavior are independent of the chain's composition.

The chain advances only for the eligible failure kinds classified in the Worker's weather provider error module, for availability, timeout, quota or rate limit, authentication or configuration, upstream failure, or invalid response, never because valid weather is undesirable or differs between providers. Attempts per request are bounded at 3, with a 3,000 ms per-attempt timeout, so a retry or fallback loop is structurally impossible. Each adapter fills the daily block from the same single upstream call it already made, so the block costs no extra attempt and the budget is unchanged; Open-Meteo asks for seven forecast days instead of three and stops at the first day it answers `null` for rather than guessing one. The two weather routes share one limiter budget, at 20 requests/60s per IP, and OpenWeather calls carry an additional best-effort daily cap inside the Worker; see ADR 0002 for both and for the honest limits of that cap.

Attribution (`origin.sourceId`) is the one controlled addition to the shared contract, as described above. Settings > Service providers reads it from the last valid stored weather snapshot and presents that provider's full attribution; no new API field is needed. The Apple Intelligence status there reuses the on-device availability probe and the last recommendation's stored generation mode.

### Target recommendation and AI flow

Deterministic rules bound the request, AI composes within those bounds, and validation gates the result twice. AI is not a personalization layer. It selects three meaningfully different outfits from catalog-only candidates that are already complete, formality-consistent and plausibly layered, avoiding previous-day repetition; colour harmony is not its job, because the catalog describes types without colour ([ADR 0007](adr/0007-ai-selects-precomposed-outfits.md) section 3).

Before either AI tier sees options, composition excludes an outfit when its garment-id set equals one of the seven most recent valid worn history rows. Invalid rows are skipped, while database read errors still propagate. Seven is a domain constant, and the repository reads the newest rows a page of seven at a time until seven valid ones are found, never the whole history. If that leaves fewer than three candidates, it relaxes the oldest exclusion first until three remain. Only the resulting catalog options cross the AI boundary; history rows and photos never do. The existing exclusion of the three outfits currently shown, by the same garment-id set, still applies when the pool permits it. See [ADR 0038](adr/0038-outfit-history.md).

```text
mobile: deterministic requirements + preference-filtered catalog candidates + day seed
        ↓  exclude the previous local day's three body-garment sets when at least three remain
        ↓  sanitized request: no Wardrobe data, photos, paths, profile/device IDs, or coordinates
routed AI client on the device
        ↓  tier 1, only when the module reports the on-device model available
on-device Foundation Models through the local Expo module
        ↓  shared contract validation, then deterministic domain invariants
        ↓  every on-device failure falls to tier 2 with the remaining budget
Worker AI route
        ↓
ordered AI chain: Haiku → Workers AI binding → OpenRouter fallback
        ↓
Worker-side runtime validation and sanitized failure mapping
        ↓  structured response: allowed candidate identifiers + closed code vocabulary
mobile: shared contract validation, then deterministic domain invariants
        ↓
persisted recommendation snapshot and localized presentation
```

The request follows the canonical [AI input privacy boundary](product-decisions.md#approved-ai-input-privacy-boundary). `/v1/ai/recommend` stays shape-frozen for strict installed readers. `/v2/ai/recommend` accepts the v1 request plus required `locale` (`tr` or `en`) and optional sorted `styleAesthetics` (at most three closed ids) and returns the v1 picks plus optional `insightSentence`, one Latin-script sentence of 1 to 90 characters without a line break or a comma, semicolon or colon at its end or before its final terminator. The Worker parses the sentence with that shared schema, then requires a complete sentence (at least four words, a closing mark, and no last word from a closed list of articles, conjunctions and prepositions that can never end a sentence, `apps/worker/src/ai/insight-sentence.ts`), and drops a failing one before the response, keeping the picks, so no installed build depends on its own validation for these rules. Shared schemas live in `packages/contracts`; the v2 response strips unknown keys. One Worker handler serves both routes and emits the sentence only on v2. Mobile sends its language and resolved aesthetics on v2. The shared AI input projection orders options best-first by formality without adding locale. The Worker v2 prompt adds locale to its instruction and four closed boolean day flags derived from requirements to its user message; the on-device input shape stays fixed.

After Zod parsing, device domain validation applies [ADR 0039](adr/0039-ai-v2-route-and-the-validated-insight-sentence.md)'s decimal-digit, per-locale language-signal and banned-content checks: Turkish accepts a closed-list function word or a Turkish-specific letter, while English requires a closed-list word and rejects those letters. The approved AI input projection contains no numeric weather, so any digit is discarded with the sentence. Failure uses the deterministic localized first insight line; invalid outfit picks still reject the selection whole. Accepted prose and its locale are optional paired fields inside `recommendation_snapshots.context_json`, so older rows parse. Today shows the prose only when its stored locale matches the current language.

Under [ADR 0034](adr/0034-on-device-ai-selection-through-apple-foundation-models.md), the composition boundary returns a routed client satisfying the existing `AiClient` interface, so the controller, the mapper, persistence, and the trigger rules keep their shape. It attempts the on-device tier only when the module answers `available`, spends at most 8 seconds there, and then gives the Worker request its own 38-second wait (the Worker's 36-second walk plus 2 seconds of transport), so the whole refresh is bounded at 46 seconds and the deterministic fallback is reached only after the last provider has failed. Mobile sends that wait minus a 1-second transport margin, 37 seconds, in a private validated header, and the Worker clamps it to its own 36-second walk; the strict request body and the Worker's shared cache identity exclude it. An unavailable answer costs no attempt and no time, so Android, web, and ineligible iPhones spend nothing in that tier. Both AI tiers pass through the same validation gate (`mapWorkerAiRecommendation` in `features/recommendation/application/ai-recommendation-mapping.ts`; the request it checks against is built in `application/recommendation-context.ts`, and only the stored-row parsing sits in the data layer, in `data/stored-recommendation-mapper.ts`), so an on-device answer the gate rejects is that tier's failure and the Worker still gets its turn; the deterministic device-local fallback keeps its place behind both and is reached by the controller's existing catch. `aiModelInputFromRequest`, `picksAreMeaningfullyDifferent`, and `meetsArchetypePrecondition` in `packages/contracts` are the one model-input projection, the one distinctness rule, and the one archetype precondition both executors use, so the field list defining what a model may see and the rules its reply is judged by exist once. The native surface is a local Expo module in Swift under `apps/mobile/modules/kuyara-on-device-ai`, declared for Apple platforms only, and `features/recommendation/data/on-device-ai-module.ts` is its only importer anywhere in the app: it exports the module or null, so application, feature, and domain code see one branch and never touch the native surface. The Service providers surface reads the module's availability, which runs no inference and consumes no quota, so the bounded Worker probe stays the only probe.

### AI contracts and Worker orchestration

The candidate source, day seed, and privacy boundary are defined by [ADR 0005](adr/0005-catalog-only-recommendation-candidates.md) and [`product-decisions.md`](product-decisions.md#approved-catalog-only-recommendation-and-wardrobe-model).

The mobile request carries at most 24 fully composed options, bounded by the shared contract as a transport and prompt-size limit. Shared Zod schemas enforce option and response structure; the Worker checks that every selected option was offered. The per-attempt timeout is injectable, defaulting to 7 seconds, so timeout behavior is testable without real waiting; the request deadline defaults to 36 seconds for an old client and otherwise uses the validated transmitted budget clamped from 5 to 36 seconds.

- **Contracts** (`packages/contracts/src/ai-v1.ts`, `POST /v1/ai/recommend`). Request carries `clothingPreference`, the `ClothingRequirement[]` discriminated union and a bounded `options` array of at most 24 precomposed outfits. Each option has a stable `optionId`, formality, garments and validated traits. Response success is `data.picks` with exactly three unique `{optionId, archetypeId}` pairs; each option id must come from the request and each archetype id is unique. Response error reuses the weather-v1 error shape with codes `invalid_request | not_found | method_not_allowed | ai_unavailable | internal_error | rate_limited`.

  Under [ADR 0031](adr/0031-dress-style-is-the-formality-signal.md) the strict v1 request accepts optional `dressStyle` (`casual`/`smart`/`formal`) so previous clients remain compatible. The v2 request additionally requires the closed locale and accepts optional closed sorted style-aesthetics IDs. Mobile supplies the day's resolved formality, and the Worker treats an absent style as `smart` in both prompt and shared cache key. Aesthetics rank already-valid options through a static twelve-archetype affinity table, with ties retaining composition order; deterministic fallback applies the same soft sort. Persisted recommendation context carries resolved formality and aesthetics for cache comparison; snapshots written with the retired field or with neither style field are read as `smart`. Birth date and birth year never leave the device or enter the shared cache key.

  Ordinary generation excludes every offered option wearing the body garments of one of the persisted snapshot's three outfits when at least three alternatives remain; the option id is not compared, because it carries the day's accessories; a narrower pool may repeat. A fresh install and a snapshot without three outfits exclude nothing. A confirmed “Ask the stylist again” request may select an option shown before. The Worker's shared cache key adds the sorted offered option ids and resolved style fields, so a cached response can never name an option absent from the current offer. When no other valid option remains, Today hides the re-ask action.

  A re-ask whose allowance was reserved sends the optional v2 field `reask: true` (the strict schema admits only `true`; v1 refuses it). The Worker then neither reads nor writes its shared cache, because the cached answer for the same offer is the trio the reader asked to replace; the burst limiter and the Workers AI daily counter count the request exactly like a first generation and refuse it at the same caps, and a signed-in member's re-asks are also counted per member by the Worker (see the member allowance under the rate-limit rules below). Every other request, the tomorrow preview included, and every installed binary that predates the field leave it out and behave as before. The field never reaches the model input, the shared cache key, analytics or a log line. A shared-cache hit logs one closed `ai_cache_hit` line carrying only the route.
- **Worker orchestration** (`apps/worker/src/ai/`). `createAiHandler({ providers })` mirrors `createWeatherHandler`'s dependency-injection shape, but takes an ordered provider list instead of one provider, so an adapter is appended without changing the handler. The deterministic in-Worker stub is a test double whose scenarios (success, invalid output, timeout, provider failure) are selected by injecting different stub instances, never by a request field. Each attempt is bounded by a per-attempt timeout (the `AbortController` race, 7 seconds); exhausting the provider list collapses to one sanitized `ai_unavailable`.
- **Worker-side validation is structural and closed-set only**, not a re-implementation of `composeOutfitOptions`'s scoring or tradeoff logic: the shared schema validates response shape and unique option and archetype ids, and the Worker verifies that each picked `optionId` was offered in the request. Invalid picks collapse to `ai_unavailable`; the specific rule that failed is never exposed to the client. Outfit composition, slot completeness and mandatory-requirement satisfaction stay in mobile, where `composeOutfitOptions` and `evaluateGarmentEligibility` already live.
- **The two endpoints that call no provider** are `GET /v1/health` (generic Worker liveness) and `GET /v1/ai/ready` (configuration readiness). The active AI provider probe from [Health, readiness, and probe distinctions](#health-readiness-and-probe-distinctions) is separate: it needs real provider quota and the Settings > Service providers "Test online AI" trigger.

### AI handler and provider adapter contract

Candidate assembly and prompt acceptance must follow [ADR 0005](adr/0005-catalog-only-recommendation-candidates.md).

- **The handler owns everything an adapter would otherwise duplicate**: the ordered walk, the per-attempt timeout, zod validation, the closed-candidate-set check, and the collapse to one sanitized `ai_unavailable`. An adapter only has to return a candidate JSON object. `createAiHandler` bounds attempts per request through a `maxAttempts` option defaulting to 5, room for the Haiku model, the two configured Workers AI models and up to two OpenRouter models, so the chain cannot loop. `HAIKU_MODELS` names only `claude-haiku-5-5`, the model `HAIKU_DAILY_ATTEMPT_LIMIT` is priced for; measured live under `wrangler dev` with the real v2 prompt, every call answered on the first attempt with picks and a sentence the handler accepted, in about 1.8 to 2.5 seconds measured at the client. `OPENROUTER_MODELS` holds the free models that, in the latest live measurement under `wrangler dev` with the real v2 prompt and reasoning off, returned picks the handler accepted inside the 7-second attempt, ordered by acceptance and then latency; a model joins only that way, and every entry is a `:free` slug. Rejected in that measurement: a provider that refuses the strict `json_schema` format, endpoints without structured outputs, a model whose reasoning cannot be turned off, and a model whose insight sentences slipped into another script or ended on a cut clause while answering close to the attempt limit.
- **The shared AI cache** is the Cloudflare Cache API (`caches.default`, [ADR 0007](adr/0007-ai-selects-precomposed-outfits.md)), read before and written after the provider walk with a 30-day `Cache-Control`. Its key is the synthetic URL `https://kuyara.internal/<route>/<SHA-256 of the canonical request>`, never the request host. The app calls the Worker's custom domain `https://api.youbrn.com` (`apps/mobile/eas.json`); the bundle embedded in build 20 and earlier binaries calls the Worker's `workers.dev` host. On the custom domain the cache works: a second identical v2 request seconds after the first is answered from `caches.default` with one `ai_cache_hit` log line, in about a tenth of the time (0.24 s against 2.4 s) and without a second provider attempt. Cloudflare documents the Cache API as functional on custom domains and on `*.pages.dev`, and as having no effect in the dashboard editor and Playground; it does not state the behaviour for `workers.dev`, and a hit there is unmeasured. The handler is correct either way (a failing or empty cache only costs a miss, pinned in `ai-handler.test.ts`), but with no hits every repeated request spends one counted Haiku attempt of the 3,245 a day, a Workers AI attempt of the 49 a day only when Haiku fails, and past those caps OpenRouter answers or the app uses its deterministic three. The same check on another host: with `wrangler tail kuyara-worker --format json` open, run `pnpm --filter @kuyara/mobile measure:ai-chain --base-url <origin> --route v2 --max-calls 1` twice a few seconds apart; a working cache logs `ai_cache_hit` for the second run and spends no second attempt. The cache is per data centre and not shared with Tiered Cache.
- **The handler's response checks go past shape.** It rejects a response whose `layerRole` is not among the matching candidate's `supportedLayerRoles`, and requires an exact `application/json` media type rather than any type merely starting with it. In the contracts, `supportedLayerRoles` has no minimum size: the canonical taxonomy gives footwear and accessories an empty role set, and an earlier lower bound rejected every request containing footwear.
- **The shared prompt surface** (`ai-prompt.ts`) holds `outfitJsonSchema`, a hand-written JSON Schema whose shape is exactly `aiRecommendV1SuccessSchema`'s, so an adapter returns parsed model output with no mapping step. It is hand-written rather than derived because the workspace is on zod 3.25.76 and the structural outfit rules live in `superRefine`, which no converter can express. Those rules stay enforced by the handler's zod parse; the JSON Schema only shapes model output and is never treated as validation. `buildMessages` passes the already-sanitized request straight through, adding and filtering nothing.
- **Output token ceilings are fixed in code, not tuning knobs.** Without a ceiling both runtimes stopped at their default length and returned truncated JSON that failed `JSON.parse` or zod. The OpenRouter adapter sends `max_tokens: 2048` and `reasoning: { enabled: false }`: with reasoning on, the free reasoning models thought past the 7-second attempt, and with it off they answered in about 1.3 to 6 seconds. The Haiku adapter sends `max_tokens: 256` (measured replies are 149 to 173 tokens), thinking off and effort `low`: thinking roughly doubled the answer time without more valid picks. The Workers AI adapter caps a recommendation at 192 output tokens, the per-attempt output that `WORKERS_AI_DAILY_ATTEMPT_LIMIT` is derived from, so a runaway reply cannot cost more Neurons than the budget assumes; the probe asks for 256 (`PROBE_MAX_TOKENS`). None of them is in `Env` or `wrangler.jsonc`. The timeouts are likewise measured bounds rather than defaults, and they are one budget across the boundary: Haiku answered in about 1.8 to 2.5 seconds and Workers AI in 2 to 4.5 seconds when measured live, while a provider that does not answer stalls indefinitely, so the per-attempt timeout is 7 seconds and `index.ts` passes no override. The Worker's own walk is bounded at 36 seconds, five attempts of 7 seconds plus one second for the rate limiter, the body parse and the cache lookup, so every configured provider gets its turn before the Worker answers `ai_unavailable`. Mobile waits 38 seconds for the request, the walk plus 2 seconds of transport, and sends that wait minus 1 second in `x-kuyara-ai-budget-ms`; the Worker validates the positive integer, clamps it from 5 to 36 seconds, and falls back to 36 seconds when the header is absent or invalid. The handler starts no attempt with less than a useful 5-second window and aborts an in-flight attempt at the request deadline. The budget does not enter the request body, shared cache identity, logs or analytics. Red line: do not raise the per-attempt timeout toward the deadline; a single stalled attempt then consumes several providers' turns. Red line: do not shorten the mobile wait below the Worker walk again; a client that aborts while the Worker is still walking its chain turns a working provider into the deterministic fallback. The probe client's 25 seconds is separate and unchanged.
- **Adapters keep sanitization at their own boundary.** The Haiku and OpenRouter adapters hold their API key in a private class field and throw only constant-message errors, so the key, the response body, the status text, and provider identity are never interpolated into an error. The Haiku adapter reads an error body only to classify it: a 402, or a 400 or 429 that names a credit, a spend limit or billing, is `quota_exceeded`; another 429 is `rate_limited`. Structured outputs reject array-size and string-length constraints, so that adapter drops `minItems`, `maxItems`, `minLength` and `maxLength` from the schema it sends, and the handler's schema and selection gate enforce them as for every provider. The Workers AI binding takes no `AbortSignal`, so that adapter calls `signal.throwIfAborted()` first and otherwise relies on the handler's per-attempt race; no second timeout exists.
- **Composition happens once per isolate.** `buildRouter(env)` runs on the first `fetch` and its result is memoised at module scope; the memo holds a `CryptoKey` promise, strings, plain configuration and handler closures, never a `Request`, a `Response` or coordinates, and every handler takes the request as an argument. Composing inside `fetch` is a red line: it makes every per-isolate cache dead, so the probe's 60-second result cache never outlives a request and the WeatherKit token provider re-imports the key and signs a fresh JWT on every weather call. `buildRouter` calls `createAiProviders(env)`, which builds the Haiku provider when `HAIKU_API_KEY`, `HAIKU_MODELS` and `DAILY_COUNTERS` are present (behind its daily cap, so never uncounted), then one Workers AI provider when the binding and its model are present, then one OpenRouter provider per configured model id in order. Per-model instances are deliberate: the handler's ordered walk *is* the model fallback chain, so no second fallback loop exists. `aiReady` is `providers.length > 0`, so `/v1/ai/ready` reports real configuration state while still calling no provider. The weather chain, the place-search provider and the probe handler are composed in the same pass.
- **The deterministic stub is never composed in production.** It survives only as an injected test double. When nothing is configured the provider list is empty, `/v1/ai/ready` reports `not_configured`, and `/v1/ai/recommend` returns `ai_unavailable`, which is the correct signal for the device-local deterministic fallback.

### Where each fallback lives

Five distinct fallbacks operate at three boundaries. Keeping them separate is what lets any one of them fail without breaking the product.

| Fallback | Location | Trigger |
| --- | --- | --- |
| Next weather provider in the chain | inside the Worker | eligible upstream weather failure |
| Last known good weather snapshot | mobile SQLite and weather repository | refresh fails after the chain is exhausted |
| Worker AI tier | mobile routed AI client | the on-device tier is unavailable, times out, fails, or its answer is rejected by validation |
| Next AI provider in the chain | inside the Worker | eligible AI provider failure or invalid structured output |
| Deterministic three-outfit generation | on device | AI unavailable, over quota, or rejected by validation |

The two Worker-side fallbacks are invisible to mobile, which sees one success or one sanitized failure. The routed client's hop from the on-device tier to the Worker is invisible to the rest of the app as well: both tiers return the same validated result and differ only in the recorded generation mode. The last known good weather snapshot and the deterministic three-outfit generation are what let the app still show weather and a recommendation with no network and no AI at all.

### Health, readiness, and probe distinctions

Three separate questions, deliberately not collapsed into one endpoint:

- **Worker liveness** (`GET /v1/health`): is the Worker running? Involves no AI provider and consumes no quota.
- **AI configuration readiness** (`GET /v1/ai/ready`): is AI configured well enough to attempt a request? Inspects configuration only and calls no provider.
- **Active AI provider probe** (`POST /v2/ai/probe`; `POST /v1/ai/probe` stays for installed binaries): will a provider answer right now? This consumes provider quota, so it is explicitly triggered, bounded, rate-limited, and briefly cached.

A successful probe describes only the moment it ran. It never guarantees that a later full recommendation request will succeed, so the deterministic fallback stays mandatory regardless of probe state.

The probe handler (`apps/worker/src/ai/probe-handler.ts`) is assembled by injection like `createAiHandler`. On each `POST` it: rejects non-`POST` with `405`; applies a per-IP burst limit (`cf-connecting-ip`) and returns `429 rate_limited` with `Retry-After: 60` when denied; returns an isolate-cached result when one is under 60 seconds old; checks its named daily counter in the `DAILY_COUNTERS` Durable Object keyed `probe:YYYY-MM-DD` and returns `429 rate_limited` at 30; then runs **only the first provider the route can name** once, against a fixed minimal in-Worker `AiRecommendV1Request`, with a 20-second timeout. `POST /v2/ai/probe` names the chain's first provider: Haiku when composed, otherwise the first remaining provider. `POST /v1/ai/probe` answers with the first provider whose id its closed `providerId` enum holds (the first Workers AI model), because installed binaries parse that enum strictly and a `haiku` member would break their Settings screen; its body is unchanged. Each route keeps its own isolate cache, and both count against the one `probe` daily cap and the one burst limiter. The result is `ok` only if the output passes the same structural and closed-candidate-set validation a real recommendation uses; any parse failure, timeout, provider error, or empty provider list yields `unavailable`. The response is `{ data: { status: 'ok' | 'unavailable', checkedAt, assistant? } }`. Only a successful answer includes `assistant` with controlled, non-secret `providerId` and `model`; failures expose no provider identity, upstream status or error text. The daily counter increments only when a provider was actually called; cache hits and rate-limit rejections do not. A v2 probe of Haiku also counts one attempt against the `ai:haiku` counter, because the capped Haiku provider increments before every call, so the paid cap stays exact; a spent Haiku budget makes that probe `unavailable` without trying another provider.

Rate limiting also covers `POST /v1/ai/recommend` (per-IP, 10/60s) and `POST /v1/places/search` (per-IP, 30/60s, keyed `places:` plus the client address through `PLACE_SEARCH_RATE_LIMIT`, namespace 1004). The place-search figure is derived, not guessed: the picker debounces typing at 300 ms, so a search session is a handful of requests, and one request costs at most four upstream Open-Meteo geocoding calls (the typed query plus at most three dotless-ı spellings), which is 120 calls a minute per IP at the cap, well under Open-Meteo's free 600 calls a minute (see ADR 0002's pricing basis). In front of the Worker, a rate limiting rule on the `youbrn.com` zone blocks a client address that sends more than 20 requests to `api.youbrn.com` in 10 seconds within one Cloudflare data centre, for 10 seconds. A blocked request never runs the Worker and does not count against the Workers Free daily request allowance of 100,000, so one address under a sustained flood reaches the Worker about 86,000 times a day; several addresses together, or any client calling `workers.dev`, which has no zone rule, can still spend the allowance. The figure leaves room for a place search typed letter by letter (one request per keystroke at least 300 ms apart) plus the weather and recommendation requests that follow it. A configuration rule on the same zone turns Browser Integrity Check off and Security Level to essentially off for `api.youbrn.com`, because a challenge page is an invalid response to the app. A WAF custom rule on the same zone blocks every request to `api.youbrn.com` except these: `GET /v1/health`, `GET /v1/ai/ready`, `POST /v1/weather`, `POST /v2/weather`, `POST /v1/places/search`, `POST /v1/ai/recommend`, `POST /v2/ai/recommend`, `POST /v1/ai/probe`, `POST /v2/ai/probe`, `POST /v1/feedback` and `POST /v1/account/delete`. The zone rule must change in the same release as `apps/worker/src/router.ts`: a new route stays blocked at the edge until it is added to the rule, and `apps/worker/src/edge-rule.test.ts` fails until this list matches the paths the router serves. All of these endpoints use native Cloudflare rate-limit bindings, keyed by the caller's IPv4 address or, for IPv6, by its /64 prefix, which one subscriber usually holds whole and could otherwise rotate through; the probe, the Haiku and the Workers AI attempts of `POST /v1/ai/recommend` and the two capped weather providers each count against their own named counter in the `DAILY_COUNTERS` Durable Object binding (`apps/worker/src/daily-counter.ts`). The Haiku daily attempt cap (`HAIKU_DAILY_ATTEMPT_LIMIT`, 3,245 in `haiku-ai-provider.ts`) keeps a 31-day month inside the monthly API credit even if every attempt costs the most it can: the cap refuses, before counting it, any prompt over 18,600 characters (`haikuPromptCharacterLimit`, the largest prompt measured from the app's own composition, rounded up), the prompt is ASCII so it is at most one token per character, and output stops at 256 tokens. The account holds no payment card, so a spent credit refuses calls instead of billing; the attempt is counted before the call and a counter failure skips the provider. The cap covers the deployed Worker only: a local `wrangler dev` with the key spends the same credit. The Workers AI daily attempt cap protects its shared Neuron pool; mild-day traffic can still raise OpenRouter volume against a shared free tier protected only by the per-IP 10/60s brake, so no second counter is added without its own decision. The deployed single environment keeps `durable_objects`, `ratelimits`, `vars`, and `ai` at the top level of `wrangler.jsonc`; see [ADR 0003](adr/0003-single-worker-environment.md). When a rate-limit binding is absent the route it guards goes offline with a 503 `*_unavailable` body and a `route_binding_missing` log line; when `DAILY_COUNTERS` is absent the AI routes go offline the same way and the weather chain runs on the uncapped Open-Meteo provider alone. Local development and unit tests supply the bindings through `wrangler dev` and the test doubles rather than through a permissive fallback.

A signed-in member's "Ask the stylist again" requests are counted by the Worker as well ([ADR 0041](adr/0041-optional-accounts.md), section 13), because the device counter is not trusted for members. A `reask: true` request to `POST /v2/ai/recommend` that carries `Authorization: Bearer <token>` is a member request when the shared Supabase token verifier (the one `POST /v1/account/delete` uses, so one cached key set) accepts the token; the `sub` is the member's user ID. The ID names one Durable Object in the existing `DAILY_COUNTERS` binding (`ai:member:<user ID>`) whose stored key is the constant `ai:member` plus the UTC day, so the object stores no user ID, and `MEMBER_REASK_DAILY_LIMIT` (10, in `apps/worker/src/ai/member-allowance.ts`) is the only place the figure lives. The eleventh re-ask of a UTC day answers the existing closed `429 rate_limited` with `Retry-After: 60`, before the cache and the provider walk, so a refused request spends nothing; the device then falls back as it does for any 429. The request carries no local day, so the day is the UTC day, like every other counter. Every other request is handled as a non-member's with no new failure: no header, a token the verifier rejects, a verifier or counter outage, missing Supabase settings, and any request that is not a re-ask (which is never verified). The member allowance never raises the global Haiku and Workers AI totals (3,245 and 49 attempts a day for everyone together), which still apply to members. The token is read only from the `Authorization` header, once, by `account/bearer-token.ts`; the user ID keys the counter only and appears in no log line, response, analytics event or AI request, and the closed lines are `ai_member_allowance_exhausted` (route only), `ai_member_verifier_unavailable` and `ai_member_counter_unavailable`. Every counter object sets an alarm for seven days after the start of the UTC day of each new key it opens; the alarm deletes only the keys whose seven days are over (an alarm can run alongside requests to the same object, so a key opened meanwhile stays) and re-arms for the earliest key left, so a member who stops asking leaves only a pseudonymous count, which is not deleted with the account and expires within seven days of its day. While no key set was ever loaded and Supabase is down, the shared verifier answers `unavailable` without fetching for one cooldown (60 s) after a failed read, so a member re-ask never waits out a fresh fetch each time.

The Worker's automatic invocation logs are off (`observability.logs.invocation_logs = false`), because Cloudflare's per-request capture records request metadata and headers, which on the account routes include the `Authorization` bearer. Its own `console` lines stay on and carry only closed event names, stages and codes, never an IP address, a header, a token, a user ID or a rate-limit key. `POST /v1/account/delete` is limited per IP at 3/60s through `ACCOUNT_DELETE_RATE_LIMIT` (namespace 1006).

**Usage counters.** Workers Logs keep three days, so the closed events that decide quota and provider health are also written as Workers Analytics Engine data points to the dataset `kuyara_usage`, bound as `USAGE_EVENTS` at the top level of `wrangler.jsonc`. Wrangler does not inherit the binding into the `e2e` environment, so a local end-to-end run writes nothing; without the binding (unit tests, `wrangler dev`) the writer is a no-op, and a write that throws is swallowed, so counting never changes a response. `apps/worker/src/usage-metrics.ts` owns every write and is injected into the AI handler and the weather chain like their other dependencies. One data point carries the event name as its only index, `blob1` as the subject, `blob2` as the outcome and `double1` as 1, so a count is `SUM(_sample_interval * double1)`. Every value comes from a closed list and a value outside it drops the point; no coordinate, place, user or profile identifier, token, prompt, model output, address or request body is ever written.

| `index1` (event) | `blob1` (subject) | `blob2` (outcome) | Written |
| --- | --- | --- | --- |
| `ai_cache` | `v1`, `v2` | `hit`, `miss` | once per recommend request that consults the shared cache (a re-ask does not) |
| `ai_attempt` | `haiku`, `workers-ai`, `openrouter` | `ok`, `timeout`, `invalid`, `quota`, `upstream` | once per provider attempt of the recommend walk; a spent Haiku cap reads `quota` |
| `weather_attempt` | `weatherkit`, `open-meteo`, `openweather` | `ok`, `timeout`, `invalid`, `quota`, `upstream`, `auth` | once per provider attempt of the weather chain; a spent daily cap reads `quota` |
| `daily_budget` | `workers-ai` | `exhausted` | once per request that finds the Workers AI daily attempt budget spent |

The Workers AI rate limit and an upstream 429 both read `quota`; the probe route is not counted. The Workers Free allowance is 100,000 data points written and 10,000 read queries a day ([pricing](https://developers.cloudflare.com/analytics/analytics-engine/pricing/)); a recommend request writes at most seven points (one cache, up to five attempts, one budget) and usually two, a weather request at most three and usually one, and the pricing page does not say what happens past the allowance. Shared cache hit rate and Haiku quota refusals over the last seven days, from the SQL API (`POST https://api.cloudflare.com/client/v4/accounts/<account id>/analytics_engine/sql` with an API token that has Account Analytics Read, the query as the body):

```sql
SELECT blob1 AS subject, blob2 AS outcome, SUM(_sample_interval * double1) AS events
FROM kuyara_usage
WHERE index1 IN ('ai_cache', 'ai_attempt') AND timestamp > NOW() - INTERVAL '7' DAY
GROUP BY subject, outcome
ORDER BY subject, outcome
```

## Account, analytics and observability boundaries

The account and sync boundary below is accepted in [ADR 0041](adr/0041-optional-accounts.md) and switched on by `ACCOUNT_SCREENS_ENABLED = true`; the Supabase client is imported only from `features/account/data/`, the native account code loads through a dynamic import only when the switch is on and the Supabase settings are valid, and otherwise the screens fail closed. The analytics boundary and its feature taxonomy call sites are implemented (see that section). Neither is extended beyond its ADR without an approved task: see [ADR 0022](adr/0022-supabase-is-the-intended-backend-and-kuyara-is-not-local-first.md), [ADR 0041](adr/0041-optional-accounts.md) and [ADR 0023](adr/0023-behavioural-product-analytics-with-posthog.md).

### Accounts and sync

Supabase Auth and PostgreSQL are the backend of the optional accounts, and Storage is the intended home of synchronized files. They attach beside the existing stack rather than replacing any of it: the Cloudflare Worker keeps its role as the boundary for WeatherKit, AI, and provider secrets, and Expo SQLite keeps its role as the store the application reads and writes first.

The repository interface is the seam, and the Supabase remote data source sits alongside the SQLite local data source under it:

```text
application controller
        ↓
repository interface                      ← the seam
        ↓                    ↘
SQLite local data source      Supabase remote data source
        ↓                              ↓
persistence record             remote record
        ↘                      ↙
          explicit mappers → domain model
```

What the code keeps for it: client-generated UUIDs, `localProfileId` on profile-owned rows, ordered migrations, `createdAt`/`updatedAt`/`deletedAt`, and four separate model families (domain, SQLite record, API DTO, remote record) joined only by explicit mappers. What it must not add: a remote data source with no caller, an outbox or operation log, a generic sync engine, or a server revision system. ADR 0041's per-row pending flag and server arrival order are the whole sync mechanism. The UUID version is pinned in one place: `isUuidV4` in `apps/mobile/src/domain/record-identity.ts` accepts only `/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i`, and `requireWardrobePhotoUuidV4` in `apps/mobile/src/features/wardrobe/domain/wardrobe-photo-path.ts` applies it to every managed photo path, so a move to UUID v7 would break every new managed photo path validated there.

Five tables carry sync-ready identity: `local_profiles`, `wardrobe_items`, `dressing_day_choices`, `dressing_day_departures` and `outfit_history` carry `id`, `created_at`, `updated_at` and `deleted_at`, and profile-owned rows carry the `local_profile_id` link. `weather_snapshots`, `weather_hourly_entries` and `recommendation_snapshots` are caches, `weather_alert_deliveries` is a device-local delivery ledger, and `active_locations` is device selection state; none of the five is synced, none of them carries `deleted_at`, and `weather_hourly_entries` has no `id` at all. History mirror photos use the managed `kuyara/history/photos/` document path, stay in device backup and never enter AI or telemetry. A deleted look keeps naming its photo until the file is removed, and opening History retries a removal that failed, as the Closet does for a deleted piece. That absence of sync identity is deliberate: a cache is refetched from the Worker rather than reconciled, and a delivery ledger describes one device. `analytics_consent`, `notifications_opt_in`, `birth_date`, `temperature_unit` and `wind_speed_unit` on `local_profiles` stay on the device and are never linked to an account; the only consent an account holds is its own sync consent record.

`updatedAt` is a device-local timestamp written from the device's own clock at write time, not a sync conflict arbiter; the weather cache tolerates a `fetchedAt` up to five minutes in the device's future (`weatherClockSkewToleranceMilliseconds`) precisely because device clocks drift against the Worker's. The account conflict rule therefore orders writes by arrival at the server (`server_updated_at`), never by `updatedAt`. Remote rows carry no schema version: a pulled row this app version cannot parse is refused at the remote boundary and the cursor still advances, and `latestDatabaseVersion` in `apps/mobile/src/infrastructure/sqlite/migrations.ts` is the device database version and stays local. The database file and every managed wardrobe photo sit in the app's Documents directory (expo-sqlite's default `SQLite` subdirectory and `kuyara/wardrobe/photos`), so both are included in the user's own device backup by default; this is deliberate, because for a person without an account that backup is the Closet's only continuity (see [ADR 0022](adr/0022-supabase-is-the-intended-backend-and-kuyara-is-not-local-first.md) section 5).

The account boundary, as [ADR 0041](adr/0041-optional-accounts.md) defines it:

- **Identity.** Supabase Auth with Apple and Google ID tokens, each with a nonce: Apple's from the native prompt, Google's from Google's sign-in page in the system browser session (`expo-web-browser`) with PKCE, exchanged with Google for the token. The session's encryption key sits in the Keychain (`expo-secure-store`, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`) and the encrypted session in `expo-sqlite/kv-store`, so a reinstall or a restored backup starts signed out. The Supabase client's own automatic refresh is off and the app lifecycle runs the token refresh only in the foreground. A session that cannot be decrypted reads as signed out; a failed Keychain or store read is not, and the session is read again at the next foreground. The Supabase client library is imported only from the account feature's data layer; UI and domain code never import it, and the app holds only the project address and the publishable key.
- **Device side.** Migration 25, after version 24, adds `pending_sync` to the five sync-ready tables and `device_account_link` for the linked user ID, last linked user ID, last pull cursor and permanent sign-in card dismissal. The repositories mark each local write, except that profile writes mark the row only when the display name, gender, dress style or style aesthetics value changes. A successful upload clears the flag when the row returns with the same `updated_at`; the one-profile rule stays. Migration 28 adds the account the phone's Closet and History joined under the sync consent and the arrival of the consent record they joined under, so a later sign-in resumes unless the consent was withdrawn since.
- **Remote side.** Each synced table has a `public` counterpart keyed by the owner and the client UUID, with `user_id` referencing `auth.users` on delete cascade, the client's lifecycle fields and a trigger-written `server_updated_at`. The daily choice and departure tables are unique on `(user_id, day_key)`; History is keyed by its UUID alone, because a day holds several looks; and the profile table holds one row per user. Row-level security is on for every synced table, with one owner policy per operation, grants to `authenticated` only and none to `anon`. Every content column has a size bound and every record table a per-user row cap, tombstones included (2000 Closet pieces, 7300 History looks, daily choices and departures each, 401 consent answers); one account's worst case is about 33 MB of disk. Because the caps bound one account and not many, the cap trigger also guards the database size in two steps: once `pg_database_size` passes 200 MB it refuses an insert, upsert or update by a signed-in account that holds more than 1 MB of rows in the four record tables, the statement's own rows included, so a few accounts at their caps cannot stop every member's sync; once it passes 400 MB it refuses every insert, upsert or update by a signed-in person, short of the Free plan's 500 MB read-only limit, which Supabase measures over every database of the project. Both steps refuse with the guard's one error. Each cap check, the size guard included, first holds a transaction advisory lock of the account alone, so parallel uploads of one account, to one table or several, count and measure one after the other and cannot pass a cap or the allowance together. Deletes, a withdrawal and account deletion still work, and recovery is deleting the abusing accounts, `vacuum full` of the affected tables and a size check. A soft-deleted row keeps no content (a trigger clears it). Insert and update on the record tables require the sync consent, and the profile accepts dress style and aesthetics only with it. A withdrawal holds a per-account transaction advisory lock alone, and every record upload, and every profile write that sets a consent field, takes it shared in a before-insert trigger and reads the consent again, so an upload and a withdrawal never interleave. The schema is `supabase/migrations/20261004120000_accounts.sql`, applied to the project, followed by `supabase/migrations/20261005090000_account_hardening.sql`, which sets the bounds, caps, guard and lock above and drops the unused profile cursor index; both files are applied to the project. `supabase/migrations/20261006120000_account_cap_locks.sql` adds the cap check lock and is applied to the project too. `supabase/migrations/20261007230000_revoke_default_privileges.sql` makes objects created later in `public` start with no access for `anon`, `authenticated` or `public`, so every later table, view or function needs an explicit grant; it is applied to the project. `supabase/migrations/20261008120000_account_size_fair_share.sql` adds the guard's 200 MB step, the same guard on updates and the one cap lock per account; it is applied to the development project and to the live project. A second Supabase project, `kuyara-dev` (Free plan, eu-central-1, the same schema and auth settings as the live project), serves development builds, and production builds use the live project. The Worker is not connected to the development project, so account deletion cannot be exercised against it.
- **What syncs.** The profile's display name and gender; with the separate sync consent, also dress style and style aesthetics, Closet items without photos, History without mirror photos, and daily choices and departures. The consent belongs to the account: withdrawing it on one phone stops sync everywhere. The account keeps a record of each consent answer with the consent text version, the time and the answer, given or withdrawn. Birth date, the analytics consent and every other consent, the notification setting, device settings, caches, `weather_alert_deliveries`, `active_locations` and every photo stay on the device, and account data never joins the AI request.
- **Member gate.** The account feature's application layer exposes one narrow `isMember` boolean selector, true for a signed-in session and never carrying an email. Outfit detail's compose row reads it through `useIsMember` (`account-membership.ts`), is absent while `ACCOUNT_SCREENS_ENABLED` is false, and for a person who is not signed in draws the `gated` press style of `components/ui` (muted but legible, never the `disabled` trait); its press opens the sign-in sheet through a `detail` value of the account sheet host, beside `profile` and `settings`, starting on the sixth benefit page.
- **Sync.** First sign-in uploads live rows and soft-deletion markers from the last 30 days. A second phone merges: Closet and History by ID, the account's daily choice or departure for a day both hold, profile fields from the account; the account's copy lands only over a row that still holds what the merge read, so an edit made while the first link runs stays pending and uploads with the next pass. Ongoing sync is last writer wins per row by server arrival, with soft deletion as a write; pulls follow the `server_updated_at` cursor, one position per table because the tables are read side by side, stored as a JSON object in `last_pull_cursor` (a single position an older build stored reads as every table's). Sync runs on sign-in, on foregrounding, on "Sync now" and shortly after a local write; the background weather-alert task never touches Supabase. A pull reads again from 10 seconds before the cursor and lands repeated rows idempotently. A pull or first link lands its rows one statement each, in transactions of 250 rows that save the cursor or link last, so the write lock never holds the app's other writes past their 5-second wait; one that stops part way runs again and lands the same way. The consent question after sign-in sets a device-local mark in the key-value store, cleared by any answer. A restored session that finds the mark, on a phone not linked to the account whose answer is still missing (or unreadable), asks the question again on the app-wide sheet and runs no pass until it is answered, and no pass runs while it checks, so a sign-in closed over the question never syncs unasked. A local write starts a pass two seconds later only while a row is pending; the account source's own writes do not notify. The session manager runs one pass at a time, and a request made during a pass gets one follow-up pass that every such caller awaits; the Supabase client sends every request through `fetchWithTimeout` with a 15-second deadline that covers reading the body, so a request that never answers, or whose body stalls after the headers, fails its pass instead of holding the later passes and the sign-out that waits for them. A pass first asks the auth port for an access token; without one (a due refresh the auth service has not answered, which the auth client keeps for a minute after a failure) the client would send the publishable key, so the pass sends nothing, shows no failure (a "Sync now" pass shows one, as a failed request) and runs again on the auth client's next `TOKEN_REFRESHED` event or the next foreground; an ended session forgets it. The in-memory development port and the closed port are the same session manager over ports that answer at once; the closed port's sign-in fails.
- **Deletion.** A new versioned Worker route verifies the Supabase access token against the cached JWKS (`iss`, `aud`, `role`, `exp`, user ID from `sub`), confirms with Supabase Auth that the token's session has not been signed out, exchanges a fresh Apple authorization code and revokes the refresh token when the app has one, then deletes the Auth user. A missing code, or one Apple refuses or that belongs to another Apple account, never blocks deletion: the account data is deleted without revocation and the result tells the app to point the person to Settings > your name > Sign in with Apple. It returns only `deleted`, `deleted_apple_unrevoked` or a closed error code; its request schema is strict and its response schemas tolerant in `packages/contracts`, and the Worker ships before the binary that calls it. Its new secrets are the Supabase secret key and the Sign in with Apple private key and Key ID. Each upstream call has a 3-second timeout, so the route's five calls end inside the app's 20-second wait; a fetched key set is trusted for 10 minutes after its last successful read and fails closed after that, and a request waits for a shared key read at most its own 3-second timeout; and an account already gone whose verified token's `app_metadata.providers` names Apple answers `deleted_apple_unrevoked`. The deletion result shows on an app-wide account sheet the tab layout hosts, over whichever tab the person is on.
- **Apple credential state.** At every launch and every return to the foreground (after the session refresh) the app calls `getCredentialState` for the signed-in account's Apple identity when this phone holds an Apple credential for that account, and ends a revoked or unknown one's session as sign-out does; while the app runs on iOS the account lifecycle hands Apple's credential-revoked notification to the manager, which ends the session under the same rule; after a failed deletion that sent Apple's code, either path first repeats the deletion with the same access token and no code. The phone holds the credential when it signed in with Apple, or added Apple, for that account, never because of the provider the account was created with; a device-local key-value entry names that account and is cleared on sign-out, deletion and a session the auth service ended. Off iOS the subscription is a no-op. Apple's server-to-server notifications stay unused.
- **Keeping the project awake.** The Supabase project stays on the Free plan, which pauses an inactive project. A Worker Cron Trigger (`17 */6 * * *`) makes one small authenticated database request every six hours, reading no person's data, so sign-in and deletion keep working.

### The analytics boundary

Product analytics attaches through a project-owned boundary, on the same principle that keeps `expo-sqlite` and provider SDKs out of features:

```text
features / application
        ↓
ProductAnalytics boundary        ← event taxonomy and the privacy filter live here
        ↓
PostHog adapter
```

Feature code emits named domain events; the boundary owns the taxonomy, enforces the payload exclusion list, and is the single place a provider swap would touch.

**Phase 1** lives under `apps/mobile/src/features/analytics/`. `domain/analytics-events.ts` is [the approved taxonomy](analytics-taxonomy.md) as types: thirty-two events with closed property unions and `schema_version`, plus `domain/analytics-mappers.ts`, the one place domain values become analytics values (`FailureCategory`, generation mode, refresh trigger, condition code), each mapper total so an unmapped domain value fails to compile. `domain/product-analytics.ts` is the port (`capture`, `optIn`, `withdraw`, `flush`); `application/error-episode-tracker.ts` and `retry-counter.ts` implement the taxonomy's per-session `error_shown` / `error_recovered` rule and the `attempt_number` cap as pure, tested logic; `application/product-analytics-provider.tsx` mounts the boundary as the outermost provider of the app shell and flushes buffered failures before the SDK on the background transition. The prerequisite the taxonomy names, a shared failure classification, is `apps/mobile/src/domain/failure-category.ts` (`offline`, `unavailable`, `rate-limited`, `unknown`); weather, recommendation and the Closet carry a `FailureCategory` in application state. It is an outbound path with its own closed exclusion list, parallel to and independent of the [AI input privacy boundary](product-decisions.md#approved-ai-input-privacy-boundary) and the Worker logging rules, and it weakens neither.

**Phase 2.** Schema version 12 stores `analyticsConsent` on the local profile and treats it as the source of truth, using `withdrawn` for both first-launch decline and later withdrawal. After onboarding, an unanswered profile sees one consent sheet per process that can be closed only by accepting or declining. Grant persists consent before constructing and opting in the SDK client, decline records no event, and withdrawal persists `withdrawn`, records the withdrawal, opts out, flushes the queued event, then severs the SDK identifier and drops the client. Settings exposes the same use case through a Privacy screen and shows the selectable analytics identifier while consent is granted and, after withdrawal, the last one from a device-only file until the person removes it or grants again. The nullable `PRIVACY_POLICY_URL` keeps the policy row hidden until a real URL is configured. When both public Expo variables are valid, the app shell configures an adapter that constructs the PostHog client at startup only for granted consent; otherwise it remains unconstructed until opt-in. Because no client exists before consent, the client initialises opted in (`defaultOptIn: true`): the SDK captures and marks its one-time application-installed lifecycle event during initialisation, so an opted-out construction would lose the install signal permanently. This satisfies ADR 0033 section 6 item 1 structurally rather than through the flag it names. While the answer is `undecided` the adapter's own consent gate drops captures: nothing is recorded or queued until acceptance, which is why the onboarding funnel that precedes the sheet is not measurable. Missing configuration uses the no-op adapter. The adapter drops every event whose name is not a catalog event, one of the five SDK lifecycle events or `$exception`, and filters the rest through the taxonomy property allowlist (each catalog event keeps only its own keys, plus reviewed SDK defaults such as `$is_emulator`, and exception fields), and disables geographic enrichment, feature flags, surveys, session replay, person defaults and push capture; only its data module imports the SDK, and guard tests reject identity APIs.

**Error Tracking follows the same consent boundary.** The client autocaptures uncaught JavaScript exceptions and unhandled rejections only after consent. Its stateful `before_send` hook applies the exception field allowlist, deduplicates by exception type and topmost in-app frame, and accepts at most five exceptions per client session. Withdrawal disposes that hook so the SDK's retained global handlers drop every later capture; a later grant gets a fresh hook. Console capture, native crash capture and exception breadcrumbs stay off. The Expo config plugin wraps native bundle phases for Hermes source-map upload, and the Metro serializer injects matching chunk ids; `@posthog/cli` 0.18.9 performs the build upload. See [ADR 0035](adr/0035-posthog-error-tracking.md).

**Phase 3 shared scaffolding.** `useScreenViewed` emits the closed `screen_viewed` event on each route focus, total mappers translate active-location sources and completed AI-probe states into taxonomy values, and `firstUses.markFirstUse` serializes per-install feature adoption through an app-private JSON file that is independent of SQLite and profiles; withdrawal clears it after severing the identity, so a re-consented install reports first use again (taxonomy 5.11). With no PostHog key, development builds use a consent-aware `console.debug` adapter so Simulator sessions expose only the event name and its already-filtered properties; production keeps the no-op fallback.

**Phase 3 call sites.** Routes, application hooks and application providers emit the taxonomy's events; presentation components emit intent. `screen_viewed` uses `useScreenViewed` in every tracked route. Weather interaction events use `use-interaction-events` at the application boundary, outfit detail and day-style events come from application hooks and the recommendation provider, and onboarding emits nothing; Settings events use thin route files. `weather_refreshed` and `recommendation_regenerated` come from the two controllers through an injected capture function with a no-op default, `error_shown` and `error_recovered` from the providers and routes that already observe a `FailureCategory`, and the Closet events from the wardrobe routes with a pure `fields_changed` helper. `age_bucket` and `dress_style` are derived at emit time by `ageBucketProperty` and `dressStyleProperty` in `analytics-mappers.ts` and are never stored. No feature file imports the SDK; the guard test in `apps/mobile/src/architecture-invariants.test.mjs` enforces the boundary.

For the daily-style and history decisions, the closed `dress_style` analytics value is the day's resolved formality, aesthetics are not measured, and logging a worn outfit emits `outfit_worn_logged` with closed values only. Display name remains forbidden free text.

### The observability boundary

EAS Observe is performance and diagnostic instrumentation, not a second analytics architecture. It attaches through its own project-owned port, `features/analytics/domain/performance-telemetry.ts` (`logEvent`, `reportError`, `setDispatching`, `discardPending`), with `features/analytics/data/observe-performance-telemetry.ts` as the single adapter and the app's only importer of `expo-observe`; `rg "expo-observe" apps/mobile/src --glob '!*.test.*'` returns that file alone. `Observe.configure()` runs at module scope in `src/app/_layout.tsx`, before any screen mounts, because the expo-router integration cannot be enabled after the tree is mounted; the same call gates dispatch on the analytics consent answer, read once and synchronously from the existing `local_profiles.analytics_consent` column through `openKuyaraDatabaseSync()` and `readAnalyticsConsentSync()`, where a missing table or any error reads as `undecided` and dispatches nothing. That answer lives in one in-memory value (`analyticsConsentState`) that every analytics gate reads and that the profile data source updates as soon as a consent write has committed, so a failed write leaves the previous value and no gate opens a database connection per call. Consent changes inside the session re-apply the configuration through the port, so withdrawal stops dispatch immediately. A grant first calls `discardPending()`, which advances Observe's native cursor past everything recorded while the answer was open, before the answer is stored, so a restart right after the write cannot deliver rows from before consent. Screens mark readiness through `useScreenInteractive`, and only three user-defined events exist, `recommendation.generated`, `recommendation.first_shown` and `weather.refreshed`, whose attribute keys and closed value vocabularies live in `domain/performance-telemetry-events.ts`. Every duration in them is a whole number of milliseconds: `weather.refreshed` and `recommendation.generated` measure around their own attempt, and `recommendation.first_shown` is sent at most once per process from `use-today-reports` when the focused Today first shows a recommendation, measured from the one start mark `data/process-clock.ts` takes at module scope in `src/app/_layout.tsx` (a monotonic read, `performance.now()`, owned by that file alone). It is not `markInteractive`, which marks Today's first draw in any state, a loading one included. Both time the launch: iOS starts the app in the background for the weather-alert task and renders the interface off screen, so `domain/launch-visibility.ts` (fed by React Native's `AppState` in `data/launch-visibility.ts`) decides once, at the first launch metric, whether the app had been in the foreground by then, and a launch first timed off screen sends neither for the rest of its process. A background process suspended before its first metric and opened later is still timed, from its unseen start; the package's own first-render, launch-time and initial-route metrics are recorded off screen and are not filtered. The same visibility counts the session (`application/launch-session.ts`): at module scope for a foreground launch, at the first foreground for a background one, never if nobody opens it. The PostHog client, whose SDK captures an app open as it is constructed, is built only once the launch is seen. Errors reach Observe only as a `TelemetryError` built from a closed code and coarse attributes, so a caught SQLite, provider or AI message cannot be forwarded. The route and query parameters the router integration would otherwise export are listed in `domain/telemetry-route-params.ts` and filtered, which also replaces the resolved URL with `urlHidden`.

## Current end-to-end data flow

1. Mobile presentation sends user intent to application services.
2. Application services read durable local state through repository interfaces and remote state through a Worker client.
3. The Worker validates input, calls privileged providers, validates their output, and returns a versioned response defined in the contracts package.
4. The mobile client validates the response before mapping it into domain state and preserves the last known good snapshot if refresh fails.

This flow operates end to end for live weather and AI recommendations. The Worker composes WeatherKit/Open-Meteo/OpenWeather for weather and Haiku/Workers AI/OpenRouter for recommendations, and an Apple Intelligence eligible iPhone runs the AI selection step on the device before the Worker is asked at all; mobile validates and persists both response types, preserves the last valid weather snapshot, and uses the device-local deterministic outfit generator when AI is unavailable. The active AI probe and endpoint rate limits are deployed. Sign-in and the synchronization of the Closet and History run for a signed-in member who gave the sync consent. Analytics has its consent-gated adapter, its consent events, and the taxonomy's feature call sites in place; the account, analytics and observability boundaries are in [Account, analytics and observability boundaries](#account-analytics-and-observability-boundaries).

# ADR 0041: Optional accounts

Status: Accepted (2026-09-30)

Implementation: the account feature is built and switched off behind `ACCOUNT_SCREENS_ENABLED`: the live Supabase and Sign in with Apple adapters, the encrypted session store, the SQLite row source, the sync consent sheet and records, the Apple credential check at launch and the revocation notification while the app runs, the Worker deletion route and the keep-alive Cron Trigger exist and are tested against fakes. The remote schema is `supabase/migrations/20261004120000_accounts.sql`, applied to the project, followed by `supabase/migrations/20261005090000_account_hardening.sql` and `supabase/migrations/20261006120000_account_cap_locks.sql`, all three applied to the project. The Worker deletion route, the keep-alive Cron Trigger and the member re-ask count are deployed. The production build profile carries the Google iOS client id (`apps/mobile/eas.json`); a build without it fails closed for Google. The shipped app has no sign-in or cross-device sync.

## Context

The first release shipped without accounts as a scope decision ([ADR 0022](0022-supabase-is-the-intended-backend-and-kuyara-is-not-local-first.md)). The approved base is: accounts are optional, Supabase Auth signs in with Apple and Google ID tokens, account deletion ships with the first account, and weather and general recommendations work without an account. What a person loses today when they change phones is their Closet and their History; that is the reason for an account.

Five tables are already sync-ready: `local_profiles`, `wardrobe_items`, `dressing_day_choices`, `dressing_day_departures` and `outfit_history`. Each has a client UUID, `created_at`, `updated_at` and `deleted_at`, and profile-owned rows carry `local_profile_id`. Two forks waited for this decision: the one-profile-per-device rule (`singleton_key = 1`) and the conflict rule, because `updated_at` is written from the device clock and cannot arbitrate between devices.

Apple requires that deleting an account created with Sign in with Apple revokes its tokens through the Apple REST API. Revocation needs a client secret signed with Apple's private key and a refresh or access token, and that token is only obtainable by validating a single-use authorization code on a server within five minutes. Supabase's native Apple flow does not keep such a token, so one server step is unavoidable.

## Decision

### 1. Identity providers

- Supabase Auth is the identity service. Sign in with Apple uses `expo-apple-authentication` and `signInWithIdToken` with a nonce. The Supabase Apple provider lists only the bundle identifier `com.ubrn.kuyara` as a client ID; the native flow needs no Services ID and no six-monthly Apple secret.
- Sign in with Google opens Google's own sign-in page in the system browser session (`expo-web-browser`, which uses `ASWebAuthenticationSession` on iOS) for kuyara's iOS OAuth client, with PKCE and the SHA-256 of a raw nonce. The app exchanges the returned code with Google for an ID token and signs in with `signInWithIdToken` and the raw nonce, the same path as Apple, so linking and the deletion confirmation use the same token. The Supabase Google provider lists the iOS client ID among its client IDs. iOS shows its system prompt for google.com before the sheet opens. kuyara uses no paid Google sign-in library, never skips the nonce check and never routes Google sign-in through Supabase's own browser redirect. Android cannot use a custom-scheme redirect for Google and settles its Google sign-in when Android work starts. Google sign-in requests the `openid`, `email` and `profile` scopes.
- Apple is asked for the email address only, never the name; the name belongs to the local profile. The email serves support correspondence and the Account screen's "which account you signed in with" line.
- A person who hides their email with Apple has a private relay address. Support replies and the data copy reach a Hide My Email address only when the sending address is registered as an email source in Apple's Sign in with Apple for Email Communication settings; it is registered before accounts open.
- The name and profile picture a provider supplies are never stored by kuyara. Supabase keeps them in `user_metadata`; kuyara copies them into no table and never reads them.
- The Supabase project has the email provider and anonymous sign-in turned off. A new project enables email sign-in by default, so setup turns it off.
- Email sign-in is not part of the first account release and is not approved. A six-digit emailed code remains a candidate for a later release, with its own decision.
- A second sign-in method is linked only manually, while signed in, from the Account screen ("Add Google" or "Add Apple"), with Supabase manual linking enabled. Supabase's automatic linking of identical verified emails stays as Supabase provides it. Trying to add a Google or Apple identity that already belongs to another kuyara account shows a system alert with one "OK" button; signing in with an existing account on the sign-in page is not an error but a sign-in to that account.
- kuyara does not buy a domain now. Google brand verification is optional and only affects the branding on Google's consent screen; it is tried with `ubrn.github.io`, and sign-in does not depend on it. A domain is bought only if that verification fails or email sign-in is approved.

### 2. The server step: Apple revocation and account deletion

Account deletion runs as a new versioned Worker route, `POST /v1/account/delete`; like `/v1/places/search`, each route carries its own version. The Worker is kuyara's only server and the owner of its secrets; no second server runtime is added. The route's request schema is strict (an optional `appleAuthorizationCode`; the Supabase access token travels only in the `Authorization: Bearer` header, never in the body) and its response and error schemas are tolerant, both in `packages/contracts`. The success body is `{ data: { status: 'deleted' } }`, or `{ data: { status: 'deleted_apple_unrevoked' } }` when an Apple identity existed and no Apple token could be revoked; the error codes are `invalid_request`, `not_found`, `method_not_allowed`, `unauthorized`, `rate_limited`, `unavailable` and `internal_error`, read through the named unknown branch. The Worker is deployed before the binary that calls it.

The flow, in order:

1. After the system confirmation, the app asks Apple to re-authorize (Face ID) and receives a fresh `authorizationCode`. A Google account re-authenticates with Google instead. If the person cancels the Apple prompt, deletion does not start; if Apple returns no code for any other reason, the app sends the request without one.
2. The app sends the Supabase access token to the Worker, with the Apple authorization code when it has one.
3. The Worker verifies the token statelessly against the Supabase JWKS: signature, `exp`, `iss` (`https://<project>.supabase.co/auth/v1`, not the bare project address) and both `aud` and `role` equal to `authenticated`. The only accepted algorithm is ES256. The user ID comes from `sub`, never from the request body. A fetched JWKS is trusted for 10 minutes after its last successful read and never after that, even while Supabase is unreachable (the request is then refused as unavailable), so a key Supabase revokes stops verifying within that time; a failed read does not extend the trust, and failed reads are retried at most once per cooldown period. Concurrent requests share one read, and each waits for it at most its own 3-second deadline, so a read that never settles cannot hold later requests. An unknown key ID triggers a refetch at most once per cooldown period, so a stream of forged key IDs cannot turn the route into a fetch amplifier; the route's per-IP rate limiter bounds the rest.
4. The Worker reads the account's identities through the Supabase admin API. When an Apple identity exists and a code was sent, also for a Google account with Apple linked, step 5 runs. When no Apple identity exists, step 5 is skipped. When an Apple identity exists and no code was sent, step 5 is skipped and the result is `deleted_apple_unrevoked`.
5. The Worker builds the Apple client secret on every request (ES256; header `kid` is the Key ID; body `iss` is the Team ID, `aud` is `https://appleid.apple.com`, `sub` is `com.ubrn.kuyara`, short `exp`), exchanges the code at `https://appleid.apple.com/auth/token` with `grant_type=authorization_code`, and immediately revokes the refresh token at `https://appleid.apple.com/auth/revoke` with `token_type_hint=refresh_token`. The `client_id` is the bundle identifier. The `sub` of the exchange's `id_token` must equal the subject of the account's Apple identity; on a mismatch the token is not revoked, so a code from another Apple account never revokes that account's token. When Apple refuses the code or the subject does not match, the Worker continues without revocation and the result is `deleted_apple_unrevoked`. When Apple cannot be reached or the revocation call fails, the answer is `unavailable` and nothing is deleted, so the person retries with a fresh code.
6. The Worker then calls `auth.admin.deleteUser`. Account tables reference `auth.users` with `on delete cascade`, so the rows go with the user. A user the admin API no longer finds counts as already deleted; when the verified token's signed `app_metadata.providers` claim names Apple, that answer is `deleted_apple_unrevoked`, so a retry after a lost answer still carries the Apple instruction. Storage deletion joins the later photo-backup decision; no bucket exists while photo backup is absent.
7. The Worker returns only a closed result: `deleted`, `deleted_apple_unrevoked`, or a closed error code such as `unauthorized` or `unavailable`. Apple and Supabase responses, tokens and internal errors never leave the Worker and are never logged.

Revocation comes before deletion whenever a token can be obtained, because a deletion that succeeds while revocation fails leaves Apple's requirement unmet with no way to obtain the token again. If revocation succeeds and deletion fails, the account and its data stay intact and the person retries with a fresh code, so the failure line's statement that nothing was deleted is true. A missing or unusable authorization code never blocks deletion, as Apple's TN3194 requires: the account data is deleted without revocation, and the result sheet tells the person to remove kuyara under Settings > your name > Sign in with Apple.

The Worker gains three secrets: `SUPABASE_SECRET_KEY`, `APPLE_SIGN_IN_PRIVATE_KEY` and `APPLE_SIGN_IN_KEY_ID`, and two non-secret variables, `SUPABASE_URL` and `APPLE_TEAM_ID`, plus the rate-limit binding `ACCOUNT_DELETE_RATE_LIMIT`. When any of them is missing, the route answers 503 `unavailable` and calls nothing. The WeatherKit key is not reused; Sign in with Apple has its own key so that each can be revoked alone. Every call to Supabase and Apple goes through an injected `fetch` with its own 3-second timeout, so the route's five upstream calls end within 15 seconds, inside the app's 20-second wait, and the ES256 signing that WeatherKit's token also needs is one shared module.

An access token already issued to a deleted user stays valid until it expires (one hour by default). Its rows are gone, so it reads nothing, and the app deletes its local session after deletion.

Apple's server-to-server notification endpoint stays empty in the first account release, as Supabase's documentation advises. At every launch and every return to the foreground the app asks Apple for the credential state of the signed-in account's Apple identity (`getCredentialState`) when this phone holds an Apple credential for that account: it signed in with Apple, or added Apple, for that account. When Apple reports it revoked or not found, the app ends the session the way signing out does (section 6). A check that fails or cannot reach Apple changes nothing. The provider the account was created with does not decide it: an account created with Apple and signed in with Google on a phone whose Apple ID is someone else's is never asked about, and an account created with Google that signs in with Apple, or adds Apple, on this phone is. The phone keeps that mark as a device-local value naming the account, and clears it on sign-out, on deletion and when the auth service ends the session. While the app runs on iOS it also observes Apple's credential-revoked notification and ends the session the same way under the same rule.

### 3. Moving device data into the account

- On first sign-in, this phone's Closet and History are added to the account automatically, once the sync consent in section 10 is given. Until then only the display name and gender go to the account. The welcome sheet states how many pieces and how many days were added; a day is a History day. When the first sync fails or cannot run, the welcome says the account is ready and that the details are added at the next sync, and claims nothing reached the account.
- What goes to the account (dress style, style aesthetics and every table after `local_profiles` only with the sync consent):

| Device table | Goes to the account | Stays on the device |
| --- | --- | --- |
| `local_profiles` | display name, gender; with the sync consent, dress style and style aesthetics | `birth_date`, `analytics_consent`, `notifications_opt_in`, language, appearance, Easier to see, the name and walkthrough prompt gates, the morning-sheet preference and every other device setting |
| `wardrobe_items` | every field except the photo | the photo relative path and the photo itself |
| `dressing_day_choices` | every field | nothing |
| `dressing_day_departures` | every field, including the departure time and its time zone | nothing |
| `outfit_history` | every field except the photo | `photo_path` and the mirror photo |

- Photos do not go to the account in the first account release. Photo backup comes later, after real photo sizes are measured, with its own decision.
- Remote schema: each synced table has a counterpart in the `public` schema. Its primary key is the owner and the client UUID, `(user_id, id)`, which never change, so a retried upload rewrites the same row instead of adding a second one, and a phone that moves its records to another account writes them there under the same UUIDs. Each row has `user_id uuid not null references auth.users on delete cascade`, the client's `created_at` and `updated_at`, `deleted_at`, and a server-written `server_updated_at` set to `now()` by a trigger that the client cannot write. The daily choice and departure tables are day-keyed and unique on `(user_id, day_key)`; History is keyed by the owner and its UUID alone, because a day can hold several looks ([ADR 0038](0038-outfit-history.md)). The profile table holds one row per user. The account also holds the sync consent records of section 10, written by the app and never edited afterwards. Every content column has a size bound and every record table a per-user row cap, tombstones included: 2000 Closet pieces, 7300 History looks, 7300 daily choices and 7300 departures, and 401 consent answers. One account's worst case at these bounds is about 23 MB. The caps bound one account, not many, so a database guard refuses every insert or upsert by a signed-in person once the database passes 400 MB, short of the Free plan's 500 MB read-only limit; deletes, a consent withdrawal and account deletion keep working, while uploads, soft deletions included, wait. Each cap check, the size guard included, first holds a transaction advisory lock of the account and table alone, so two parallel uploads of one account count one after the other and cannot pass a cap together. Recovery is by hand: the abusing accounts are deleted, the space is reclaimed with `vacuum full` of the affected tables (deleting rows does not shrink the files), and `pg_database_size` confirms that the database is back under 400 MB. Remote records, SQLite records and domain models stay separate, joined by tested mappers.
- `local_profile_id` stays a device link, is never uploaded, and is never used for ownership checks, because the client can write any value into it. A pulled row takes this phone's profile id. The remote profile row is keyed by `user_id`.
- A pulled row that this app version's schema or catalog cannot parse (written by a newer version) is refused at the remote boundary, never overwrites a local row, and the cursor still advances. Remote enum values are as frozen as the v1 contracts.
- The first upload sends live rows and soft-deletion markers from the last 30 days.
- A soft-deletion marker carries no content to the account: the app sends it without its content, and a server trigger clears every content column, keeping only the ID, the owner, the day key and the clocks, so other phones still learn the deletion.
- The one-profile-per-device rule (`singleton_key = 1`) stays. The account link lives in a new device table holding the linked user ID, the last linked user ID (kept after sign-out), the account this phone's Closet and History joined under the sync consent (kept after sign-out, cleared when a sync finds no consent), the last pull cursor and the persisted sign-in card dismissal flag. An account other than the last linked one always takes a first link. Signing back in to the last linked account resumes and uploads pending edits, except that under the consent it takes a first link when the records have not joined it or the consent was withdrawn after they joined.
- Pending changes: each of the five tables gains a `pending_sync` flag. Every local write sets it, except that on the profile only a write that changes the value of one of the four synced fields does; a successful upload clears it when the row returns with the same `updated_at` (day-keyed tables match on `(day_key, updated_at)`). This is not an outbox or an operation log: the row's latest state is sent. The "N waiting" counts on the Account screen come from these flags.
- Migration 25 adds the flags and the link table, tested with an upgrade from the last released schema and a realistic device-database replay. Existing rows start with the flag unset. Released migrations never change. The migration ships in the first binary after build 17, with the account code present but switched off, and is never delivered by an over-the-air update to an earlier binary. Migration 28 adds the link's two joined-account columns (the account the records joined and the arrival of the consent record they joined under), additive and nullable.

### 4. Merging and the conflict rule

- On a second phone where both the account and the phone hold data, the two merge. The Closet and History merge by ID, and when the same ID exists on both sides the account's copy wins; the same piece added separately on two phones can remain as two rows, and both phones' looks of one day stand side by side. For the day-keyed tables, when both hold a record for the same day, the account's record stays. Display name and gender come from the account, and so do dress style and style aesthetics when the sync consent is given. A result sheet states the counts.
- Duplicate pieces are never removed automatically. The merge result sheet offers "Open Closet" so the person can delete one.
- When the account's copy of a History look wins, this phone's mirror photo stays with that look and is not deleted. Photos are not synced, so the look has no photo on other phones.
- The local profile stays authoritative for product logic: it reads profile fields only from the local profile, and the person edits them only there. The account's copy is their durable record; a merge writes it to the phone once, and afterwards every edit goes to the account. Birth date never goes to the account.
- Ongoing sync resolves conflicts per row by last writer wins, ordered by **arrival at the server** (`server_updated_at`), never by device clock. A soft-deletion marker is a write like any other. In day-keyed tables the identity is `(user_id, day_key)`: a same-day write arriving with a different UUID overwrites the existing row, and the phone adopts that row's ID on its next pull.
- Pulls use the `server_updated_at` cursor, so clock skew cannot reorder them. The tables are read side by side, so each keeps its own position: a late arrival in a long table never moves a short one past a row that committed there after it was read. A gap remains within one long table, most likely at a large first link: its pages are read one after another, so a row another phone commits there while later pages are read, stamped before a page already read and more than the overlap before the table's last arrival, is missed until that row is written again. The trigger stamps a row with its transaction's start time, so a pull reads again from 10 seconds before the cursor (longer than the 8-second statement timeout of the `authenticated` role) and lands the repeated rows idempotently; the cursor itself never moves back.
- Ongoing sync uploads before it pulls and skips the pull when the upload fails; a pull never overwrites a row that is pending. The first link is the exception: it pulls and merges before it uploads, and the account's copy lands over the phone's pending rows the merge read; a row changed while the first link runs keeps its edit and its pending flag and uploads with the next pass, where its later arrival wins.
- Sync runs on sign-in, when the app comes to the foreground, on "Sync now", and shortly after a local write. The background task (weather alerts) never touches Supabase.
- Passes run one at a time. A request made during a pass gets one follow-up pass after it, which every such request awaits, so a write that lands during a pass is still sent. Every account request, sign-in and sign-out included, is aborted after 15 seconds, so a request that never answers fails its pass instead of holding every later pass and the sign-out that waits for them.

### 5. Sign-in surfaces

- Sign-in is offered in two places: a dismissible card on the Profile tab and an always-present Account group in Settings, directly above the Profile group ([ADR 0030](0030-settings-as-a-native-grouped-list.md) section 2). The card's close button hides it for good.
- Both the Profile card and the sign-in page are titled "Complete your profile" / "Profilini tamamla". Under the title the page shows six benefit pages that swipe sideways, starting at the leftmost: the Closet comes back on a new phone or after a reinstall, History stays with the account, more "Ask the stylist again" requests (section 13), the same Closet on two phones (section 4), photo backup marked as coming soon, and last a sixth page, "Build from the pieces you choose" / "Seçtiğin parçalarla kombin", one title and one sentence drawn with kuyara's garment artwork, which outfit detail's gated row opens the page on (below). The photo page states that photo backup is not available yet; section 3 is unchanged, and photos do not go to the account in the first account release. Each page states one benefit in a short title and one sentence and draws it with kuyara's own garment artwork; no page says where data is kept, shows a storage symbol or calls the data safe. A dot indicator sits under the pages, with a small pause and play control beside it drawn as a system symbol. Each dot is drawn small but answers a full 44-point touch target, jumps to its page, and is spoken as its position ("Page 2 of 6"); the control's spoken label names its action, pause or play. The pages advance on their own about every six seconds in one pass and stop on the last; a swipe, a tap on a page, a tapped dot or the pause control stops them, and play resumes from the page shown. After the last page the control offers play, which runs one more pass from the first page. The pages never advance while a screen reader runs, and the control is hidden then, nor while the app is in the background. Below them, fixed while the pages move, are the Apple and Google buttons of equal size at thumb reach, a centred "Not now", and a footnote whose first sentence states that weather and outfit suggestions work without an account, "Hava ve kombin önerileri hesap olmadan da çalışır." / "Weather and outfit suggestions work without an account.", and whose second sentence states that continuing accepts the Account terms, "Devam ederek Hesap koşullarını kabul edersin." / "By continuing you accept the Account terms.", and below it a row of two links, to the Account terms in the app's language and to the privacy policy, each a full 44-point target. The page has no checkbox. The footnote never says the app works the same, because one feature is members only.
- After a successful Apple or Google sign-in, a compact sheet asks for the sync consent (section 10). Its subtitle lists what syncs, "Gardırobun, geçmişin, stil tercihlerin, günlük seçimlerin ve çıkış kayıtların da hesabınla gelsin mi?", with its English counterpart. It holds one unticked checkbox, "Evet, kayıtlarım eşitlensin." / "Yes, sync my records.", a "Metni aç" / "Read the text" control that expands the full consent text in place, and a "Devam" / "Continue" button that works with the box unticked; continuing unticked declines the consent and completes sign-in. The sheet has no terms checkbox and asks no one to confirm that they have read the privacy notice. The first upload waits until this sheet closes. The sheet also asks when the account's answer could not be read, and no sync runs from sign-in until it is answered. The phone keeps a device-local mark while the question is open and clears it on any answer, ticked, unticked or by closing the sheet. If the app is closed while the sheet asks, the restored session at the next launch or foreground finds the mark and asks again, on the app-wide sheet, before any pass runs, as long as the account still holds no answer (or it cannot be read) and this phone has not linked to that account; a person who answered is not asked again, even when the first link has not run yet.
- A cancelled sign-in is not an error: a neutral status line with an information mark says so and invites a new choice. Being offline shows a warning line as the page opens, with the buttons still enabled; a provider failure shows an error line that suggests retrying or using the other provider. On iOS each of these lines is also spoken when it appears.
- On a new phone the sign-in sheet can be closed while the first link runs. It does not reopen when the first link finishes; the Account screen and the Settings row show "Up to date" and the new counts.
- A sync failure never discards pending changes: it states how many are waiting, and "Sync now" becomes "Try again".
- Onboarding gains no sign-in step. Exactly one feature is gated behind an account: the "Build from a piece" / "Bir parçayla kombin kur" row on outfit detail, which composes the rest of an outfit around up to three chosen catalog pieces ([product decisions](../product-decisions.md#approved-manual-mix)). `ACCOUNT_SCREENS_ENABLED` hides it from everyone, the row and its sheet absent, until accounts open. Once they are open, a signed-in member uses it directly; a person who is not signed in sees the row muted but legible (text at least 4.5:1, glyph at least 3:1 in a derived ink, never the `disabled` trait or the dimmed trait) with a "Members" / "Üyelere özel" chip, and tapping it opens "Complete your profile" as a sheet from detail, starting on the sixth benefit page. The account feature exposes one narrow `isMember` boolean selector, true for a signed-in session and carrying no email, `components/ui` owns a `gated` press style, and the sheet host gains a value for detail beside `profile` and `settings`. Accepted risk: the row needs no identity, and Apple's guideline 5.1.1(v) says people can use an app without a login unless it has significant account-based features, so App Review may object.

### 6. Signing out

- Signing out keeps everything on the phone, and kuyara continues without an account.
- If there is a connection, pending changes upload before sign-out. Without one, sign-out still proceeds and the flags remain. Signing back in with the same account syncs silently.
- Signing in with an account other than the one this phone was last linked to asks nothing: the phone links to it the way a first link does (sections 3 and 4). This phone's Closet and History, including changes the previous account had not synced yet, are added to the new account and merged with what it holds, and the merge result sheet states how many pieces and days came from this phone. The previous account keeps what it already received, and nothing on the phone is removed.
- The session is deleted locally; an issued access token stays valid until it expires.
- After sign-out, Settings shows a neutral information row under the Account group. It disappears on the next visit to Settings, and the ordinary benefit footnote returns.

### 7. Account deletion

- Deletion removes everything in the account (section 2); what the phone shows stays, and kuyara continues without an account. The device's account link, the last linked user ID, the account the records joined, the pull cursor and the session are cleared and the pending flags reset; the reset keeps the sign-in card dismissal.
- Deletion lives in the app, under Settings > Account, two taps away. Its confirmation is the deletion page, the system's "Delete your account?" alert, then a fresh Apple (Face ID) or Google authorization. The page states how long deletion takes and that the person is told when it finishes.
- Deletion cannot start offline; the button is disabled with a warning line.
- While deletion runs the person may go anywhere in the app. The work continues, and when it finishes the result sheet appears wherever they are. A failure re-enables the button with an error line stating that nothing was deleted.
- When the result is `deleted_apple_unrevoked`, the result sheet also tells the person to remove kuyara under Settings > your name > Sign in with Apple (section 2).
- After the result sheet closes, Settings shows a one-time confirmation row under the Account group. It disappears on the next visit to Settings, and the ordinary benefit footnote returns.
- The Free plan has no daily backups, so the only backups are the ones taken by hand. Each manual backup is encrypted, and its key is kept separately from the backup. A deleted account's data can remain in a manual backup until that backup is removed. A backup is restored only if the account database is lost; a restore can bring back an account deleted or a consent withdrawn after that backup was taken, so every member is then emailed about the restore, and such an account is deleted, or such records removed, again at the member's request. No list of deleted accounts is kept to replay deletions automatically. The retention for manual backups is fixed before accounts open, and the privacy policy states it.
- Analytics is not linked to the account (section 12), so PostHog holds no account data to delete.
- The Worker's per-member AI re-ask counter (section 13) keeps only a pseudonymous count under an object named by the user ID and holds no user ID in what it stores; it is not deleted with the account and expires on its own within seven days.

### 8. What never leaves the device

`birth_date` (the account tables have no such column), `analytics_consent` and every consent other than the account's sync consent record (section 10), `notifications_opt_in`, the caches (`weather_snapshots`, `weather_hourly_entries`, `recommendation_snapshots`), `weather_alert_deliveries`, `active_locations`, device settings such as language and appearance, photos and photo paths. Account data never enters an AI request; the [AI input boundary](../product-decisions.md#approved-ai-input-privacy-boundary) is unchanged. Sync payloads, logs, analytics and telemetry carry none of these fields, and a test proves it.

### 9. Session storage

- After the app is deleted and reinstalled, the session starts signed out and one tap signs back in. The encryption key lives in the Keychain with `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` (`expo-secure-store`) and the encrypted session in `expo-sqlite/kv-store`. The key does not travel in backups, so another device restored from an iCloud backup cannot open the session.
- The Supabase client's own automatic refresh is off; the app runs the token refresh in the foreground only and stops it in the background.
- A stored session that cannot be decrypted reads as signed out. A Keychain or store read that fails is not read as signed out; the session is read again at the next foreground.

### 10. Region, data protection and consent

- The Supabase project is in Frankfurt (`eu-central-1`), inside the EU. The region cannot change later, and the project address is built into the binary.
- Every Supabase region is outside Turkey, so KVKK article 9 applies. Accounts open on Supabase's Data Processing Addendum, which its Terms of Service incorporate for every organization, with its standard contractual clauses, the privacy policy's account section and the separate sync consent below. kuyara does not request the Personal Data Protection Authority's separate standard contract from Supabase; on legal advice, the DPA and its clauses are enough.
- KVKK article 6/1 lists dress as special-category data. Closet items, History, daily choices, departure records, dress style and style aesthetics are treated as possibly special-category: their sync is turned on by a separate explicit consent, and the Board's adequate measures apply (below). The consent covers these six kinds of records; the departure records carry the departure time and its time zone. It is asked on the consent sheet that follows a successful sign-in (section 5), and the first upload waits until that sheet closes. The consent text is separate from the privacy notice and from the Account terms, and no surface asks the person to approve that they have read the notice (KVKK Board principle decision 2026/347; decision 2021/389 fined a bundled box). Declining still completes sign-in, and only the display name and gender sync; the Account screen offers the same consent later and lets the person withdraw it. The consent belongs to the account, not to a phone: withdrawing it on one phone stops sync on every phone signed in to that account and deletes the account's copies of the six kinds of records, and giving it later on any phone turns it on for the account. An upload and a withdrawal of the same account run one at a time under a per-account database lock, so no upload commits a copy into a withdrawn account: an upload that waits behind a withdrawal is refused, and a withdrawal that waits behind an upload deletes what that upload wrote.
- The account keeps a record of every sync consent answer, so kuyara can prove the consent: the version of the consent text shown, the time and the answer, given or withdrawn. A withdrawal is recorded the same way. These records are the only consent the account holds; the analytics consent and every other consent stay on the device.
- The Board's adequate measures for special-category data (decision 2018/10) are kept from the day accounts open: two-step sign-in on the Supabase, GitHub, Cloudflare and Apple Developer accounts; encrypted manual backups whose key is kept separately (section 7); the machine-readable data copy sent encrypted, never as a plain e-mail attachment; a breach log and a 72-hour notification runbook covering the KVKK Board's form and GDPR; and written answers to access, correction, deletion and objection requests within 30 days under KVKK and one month under GDPR.
- A copy of the data is requested by email and is sent as a machine-readable JSON file, encrypted, within 30 days. Requests have 30 days under KVKK and one month under GDPR; breach notification is 72 hours under both.
- kuyara sets no minimum age of its own for an account. It relies on the age limits of the Apple and Google accounts that sign in, shows no age declaration and never uses the birth date; no age or birth date leaves the device. The sync consent is asked of every person the same way, with no separate age rule.
- The Texas, Utah and Louisiana app-store age laws add nothing to the account binary: no Declared Age Range check and no significant-change permission.
- kuyara appoints no EU representative.
- App Privacy adds Email Address, Name (the display name), User ID and Other User Content, which covers the Closet, History, daily choice and departure records and the synced profile fields (gender, and with the sync consent dress style and style aesthetics), all linked to the user, for App Functionality, with no tracking. Photos is added only when photo backup arrives. The privacy manifest carries the same types and ships in the binary. The privacy policy (Turkish and English) is published before the account binary.
- A short Turkish and English "Account terms" page is published beside the privacy policy and linked from the sign-in page, whose footnote states that continuing accepts them (section 5); no checkbox asks for that acceptance. Apple's standard licence agreement remains the app licence.
- User-facing copy never says where data is kept. Sign-out and deletion screens say what remains in whole sentences without naming a place, such as "Your Closet and History stay in kuyara". The sync consent text is the one account surface that carries storage and transfer wording, because the law requires it there.

### 11. Spending limits and plans

- The Supabase project stays on the Free plan, in testing and after accounts open. Postgres is the authority for account data. The Free plan has no daily backups, so backups are taken by hand (section 7). It also pauses a project that shows too little database activity over a week, and a paused project stops sign-in and deletion, including during App Review. A Worker Cron Trigger therefore makes one small authenticated request to the project's database every six hours; it reads no person's data and, like the deletion route, calls nothing while the Supabase settings are missing.
- No paid Supabase plan and none of its add-ons (point-in-time recovery, custom domain, IPv4, log drains) are enabled; moving to a paid plan needs its own decision. No automatic top-up and no pay-as-you-go overage.
- The Worker stays on its free plan; the new route reads the JWKS from cache, and the Cron Trigger runs four times a day.
- Prices and quotas are reread from the official pricing pages at implementation time. This ADR freezes no price.

### 12. Security baseline and analytics

- From the first remote migration: row-level security on every synced table; one policy per operation with `user_id = (select auth.uid())`, plus `with check` on insert; explicit grants to the `authenticated` role and none to `anon`; no `raw_user_meta_data` in any policy condition; the new publishable and secret key types.
- The app contains only the project address and the publishable key. The Supabase client library is imported only from the account feature's data layer; UI and domain code never import it.
- PostHog is never linked to the account: `identify()` is never called, and analytics stays on its install identifier. Neither `localProfileId` nor the Supabase user ID becomes an analytics identifier.
- Account analytics report outcomes only, as closed values under [taxonomy 5.12](../analytics-taxonomy.md): the sign-in provider and result, the sync trigger and result, the deletion result, a failure category and an explicit sign-out. They carry no account id, email, name, provider subject, token, timestamp or row count, and they follow the analytics consent like every other event.

### 13. Member AI allowance

- A signed-in member gets 10 "Ask the stylist again" requests per UTC day; everyone else keeps 5 per install per local day, the device allowance that exists today. The Worker counts members' requests on the UTC day, because no request carries the person's local day; the device counter is not trusted for members.
- The member allowance is enforced from the first account release, when accounts open; until then every install keeps 5. The Worker identifies the member from the verified Supabase access token as in section 2 (user ID from `sub`), sent only in the `Authorization: Bearer` header, so no request or response shape of a shipped route changes. The user ID keys the counter and is never logged, sent to analytics or placed in an AI request; the [AI input boundary](../product-decisions.md#approved-ai-input-privacy-boundary) is unchanged.
- The Worker's daily Workers AI total is 49 attempts for everyone together. The member allowance never raises it, and no paid model joins the chain for members. When the total is spent, recommendations fall back to the on-device deterministic choice, for members too.

## Red lines

- No outbox, operation log, server revision system or generic sync engine without a measured need. The per-row pending flag and the server timestamp are enough.
- The device clock never arbitrates a conflict.
- An account is never required. Onboarding gains no sign-in step, and weather, recommendations, the Closet, History and manual mix work without an account; only composing around chosen pieces is members only.
- Birth date, the analytics consent and every consent other than the account's sync consent record, the notification setting, caches and device settings never leave the device.
- The Supabase secret key, the Apple private key and client secrets never enter the app, Git, an `EXPO_PUBLIC_` variable or a log.
- Account deletion is never a deactivation. A missing or unusable Apple authorization code never blocks deletion; when a token can be obtained, deletion is never reported as finished before it is revoked, and when none can, the result tells the person how to remove kuyara under Settings > your name > Sign in with Apple.
- `localProfileId` and the Supabase user ID are never analytics identifiers.
- The Closet and History are never recommendation candidates, pins or AI input.
- Supabase anonymous sign-in is never used.
- No account surface says where data is kept, apart from the sync consent text.
- No minimum-age rule or age declaration for accounts, and the birth date is never used to gate one.
- Sync consent is never per phone: withdrawing it stops sync for the whole account.
- Declining the sync consent never blocks or undoes sign-in.
- The sync consent text is never bundled with the privacy notice or the Account terms, no box is ever pre-ticked, and no surface asks the person to approve that they have read the notice.
- The member allowance never raises the Worker's daily Workers AI total and never pays for a model.
- No paid Supabase plan without its own decision.

## Consequences

- The first account binary is a native change (the Sign in with Apple entitlement, `expo-secure-store`, the privacy manifest): it needs a new binary with a date-stamp bump, an independent review of the migration, native configuration, credentials, and consent and data-collection surfaces, and a migration replay on a device database. Each new dependency is justified and checked against the current Expo SDK before it is added.
- The Worker gains secrets, one route and one Cron Trigger; its role does not change.
- Opening accounts needs the Supabase project, the Apple key and the Google client set up. Acceptance includes physical-iPhone evidence for Sign in with Apple and revocation, which the Simulator cannot provide.
- Photo backup, email sign-in, a member AI allowance above 10 a day and Apple server notifications each come with their own decision.
- The project stays on the Supabase Free plan: there is no daily backup, encrypted manual backups are taken by hand, and the Worker's scheduled request keeps the project from pausing.
- The privacy policy, the support page and the account terms page are rewritten before the account binary ships.

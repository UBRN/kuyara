# Current Project Status

## Current State

- **Mobile:** Expo SDK 57, React Native, Expo Router, and Expo SQLite provide an accountless onboarding flow; three primary tabs, Today, Weather, and Profile, with Wardrobe and Settings as Profile stack destinations; private Wardrobe photos; Turkish/English localization; and System/Light/Dark appearance.
- **Weather:** Mobile preserves the last valid snapshot, refreshes data older than 30 minutes, and reaches providers only through the Worker. The deployed chain is Open-Meteo followed by OpenWeather, with bounded attempts, runtime validation, attribution, rate limiting, and a best-effort OpenWeather daily cap. The deterministic provider is test-only.
- **Recommendations:** The deterministic layer composes at most 24 complete, valid, requirement-satisfying, formality-consistent outfits from the bundled catalog. The AI selects exactly three of them and labels each with one archetype identifier from a closed twelve-entry list; the Worker uses Workers AI followed by OpenRouter and validates option membership, count, distinctness, and archetype preconditions. Mobile persists the result and falls back to a device-local deterministic generator that assigns archetypes by the same rules. Generation triggers by comparing current signals against the persisted recommendation snapshot's signals, not an in-memory baseline. Today and outfit detail show the archetype name as the outfit title. Today and Settings expose only the coarse generation mode, and Settings includes the bounded active AI probe.
- **Notifications:** N1 is complete. Schema v6 stores `notifications_opt_in`; Settings owns the permission flow and OS-settings redirect; notification taps open Today; and the test action is development-only. N2 weather-alert rules and background rescheduling are not implemented.
- **Builds:** iOS is the first release target. EAS production credentials, a production build, and an App Store Connect record (`com.ubrn.kuyara`, ASC app `6806664440`) exist; build 1.0.0 (2) is on TestFlight internal testing and was verified on a physical device against the deployed Worker. EAS preview and production profiles use the deployed Worker; development keeps its local Worker fallback. Shared code remains Android-compatible, but Android validation is deferred.

The MVP still has no account, cross-device sync, behavioral analytics, or server-sent push. Production WeatherKit is not implemented.

The carve-out ([ADR 0009](adr/0009-a-design-language-layer-and-its-deferral-carve-out.md)) exempts role-shaped additions, a colour, typography, spacing, elevation, border, or motion role, from `design-system.md`'s "current product use" requirement, which still governs concrete variants and primitives unchanged. The deferred set was resolved together rather than one item at a time ([ADR 0010](adr/0010-status-colours-destructive-variant-and-defined-borders.md)): status tokens and the destructive button variant are approved, a new `borderDefined` neutral is approved, an info colour role is decided against permanently (info stays `brandAccent`), and the remaining primitive-shaped items, generic text-input/selector/switch/modal frameworks, non-scrollable/keyboard screen behaviour, and platform-color adapters, stay deferred. Seven new colour roles were added and measured: `successInk`/`successContainer`, `warningInk`/`warningContainer`, and `dangerInk`/`dangerContainer` in both appearances, each ink tuned so its contrast against its own `surface` sits within ±0.8 of `brandAccent`'s, plus `borderDefined` (light `#5C7A83`, dark `#527E90`), which closes a live WCAG 1.4.11 failure: an unselected Wardrobe filter chip and an outline button were identified only by a `borderSubtle` boundary measuring 1.515:1 on the white card, below the 3:1 non-text threshold, in both the shipped product and the mockups. ## Known Issues and Manual Verification Gaps

- Primary tab labels truncate at the largest accessibility text size; accessible names remain complete. This needs re-checking after the native tab bar migration (Milestone B), because label rendering moves from JS to the platform.
- In the dark theme `backgroundElevated` and `surface` resolve to the same value, and the dark elevation shadows are deliberately faint because the dark surface step already carries the separation. An elevated card therefore separates from the ground but not from a plain surface. No screen depends on that distinction today, so no dark tint was added for it.
- `.maestro/flows/update-settings.yaml` was updated for the three-tab navigation, reaching Settings through the Profile tab and its header button, but has not been executed since. It needs one `pnpm e2e:ios` run on a Simulator to confirm.
- The resolved Android manifest has not been checked after blocking fine-location permission through Expo configuration.
- Real-device VoiceOver focus order and spoken grouping remain unverified for the weather card.
- N2's background execution cannot be verified on the iOS Simulator and will require a physical-device check.
- A generated local iOS project may need its own ignored `.xcode.env.local` Node path before native builds.
- The neuron cost per call has not been measured against a live Workers AI call; ADR 0007's figure is still an estimate, not a measurement.
- The Profile wardrobe "wanted" row opens the wardrobe screen but cannot pass an initial filter, so it lands on the default owned filter. Passing an initial filter is not currently supported by that route.
- Wardrobe list item rows, with their 56pt tile and colour swatch, have still never been seen on the Simulator because the Simulator profile has no saved items.
- Android rendering of the icon set, the garment artwork, and the new picker screens is unverified; only iOS was checked.
- Real-device VoiceOver verification of the Profile location section, the per-slot outfit rows, and the new picker screens has not been done.
- `outerwear` reads as near identical to `top` at UI size (both a torso garment, distinguished only by an open front), and `accessory` is ambiguous between a hat and a bag. Redrawing both is part of Milestone B.
- A seventh status site exists that [`design-language.md`](design/design-language.md) Law 9's list of six does not name: `profile-screen.tsx`'s location status row draws its `checkCircle` in `iconPrimary`, so "recommendations are working" is still a neutral glyph. It was found during the Milestone A Simulator pass and deliberately left unchanged, because the enumerated scope was six sites and the no-location branch's status kind (warning or plain information) has not been decided.
- In the dark appearance `brandPrimary`, `brandAccent`, and therefore every filled button and selected chip resolve to the same Quiet Sky, so the wardrobe list can show three filled elements at once against Law 1's one-accent-fill-per-viewport rule. This is a palette property of the dark theme rather than anything Milestone A changed, and fixing it would mean giving filled buttons a distinct dark role.
- [ADR 0010](adr/0010-status-colours-destructive-variant-and-defined-borders.md) states the destructive button's light label as `#FFFFFF` measuring 7.53:1 on `dangerInk`, but the appearance's on-brand colour is Cloud White `#EFF4F3`. The implementation follows the rule's wording and uses `textOnBrand`, which measures about 7.1:1, still far above the 4.5:1 threshold. The ADR's illustrative hex is the part that is off, not the decision.
